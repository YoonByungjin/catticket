# 0008. KOPIS Open API のデータ範囲と、人気急上昇の順位の変化の計算方式

- 日付: 2026-11-05
- 状態: 採用（2026-11-05、人間が決定）
- 置き換え: **0003 を置き換える**（0003 の「対象はまずコンサート・ミュージカル」を全ジャンルに広げ、統計・評判のデータを加える。0003 のコインロッカーの項は 0009 で扱う）。0003 の状態は「置き換え済み（→ 0008）」
- 関係する要件: F-01〜F-04, F-08, F-09, F-29, F-31〜F-34（U-15, R-47, O-08, R-48〜R-56）

## 背景

- 公演情報は公開データから1日1回自動で収集する（F-08）。全ジャンル（F-08 ③）、ソウルだけ（F-08 ④）。
- 統計・評判の機能（F-29, F-31〜F-34）のデータの出どころを決める必要がある（U-15）。企画書 8. に、PM が KOPIS 開発ガイド v5.0 で確認した候補がある。
- 人気急上昇（F-33）の順位の変化の計算方式（R-47、O-08）を決める。
- この ADR の最初の提案で挙げた要件の解釈は、人間が 2026-11-05 に決めた（要件定義書 7.5、R-48〜R-56）。この ADR はそれに従う。
  - 人気順位（F-29）・人気急上昇（F-33）の期間は、**暦の日・暦の週（月曜〜日曜）・暦の月**で区切り、表示するのは**終わった直近の期間**（R-48・R-52）。
  - 上演回数（F-32）は、開幕からの累計（R-49）。
  - ジャンル別トレンド（F-34）は、ソウルに絞れなければ全国の割合を「全国基準」と示して表示する（R-50・R-55）。期間は「直近30日」のまま。
  - 人気急上昇の対象は、現在の期間の上位10位だけ（R-51）。現在・直前の両方の期間で、非表示の公演を除いて振り直した順位を使う（R-54・R-56）。
- 0003 は「対象はまずコンサート・ミュージカル」としており、全ジャンルの要件（F-08 ③）と合わない。

## 決定

### 1. 使う KOPIS のサービス

| 要件 | KOPIS のサービス | 使う項目 |
|---|---|---|
| F-01〜F-04, F-08, F-09（公演・会場） | 公演目録 `pblprfr` → 公演詳細 `pblprfr/{mt20id}` → 公演施設詳細 `prfplc/{mt10id}` | 公演 ID `mt20id`、公演名、期間、ジャンル、状態、出演者、予約先 `relates`、施設 ID `mt10id`、会場の緯度・経度 `la` `lo`、住所 |
| F-29（人気順位）, F-33（人気急上昇） | 予約状況板 `boxoffice` | 順位 `rnum`、公演 ID `mt20id` |
| F-31（受賞作バッジ） | 受賞作目録 `prfawad` | 公演 ID、`awards` |
| F-32（ロングラン・オープンラン） | 公演目録・公演詳細の `openrun`、公演別統計 `prfstsPrfBy` の上演回数 `prfdtcnt` | — |
| F-34（ジャンル別トレンド） | ジャンル別予約統計 `boxStatsCate` | ジャンルごとの予約数 |

F-30（評価）は KOPIS にデータがないため、自分たちのレビューで計算する（KOPIS は使わない）。

### 2. 公演の収集の範囲（F-08）

- 地域: ソウル（`signgucode=11`）。
- ジャンル: 指定しない（全ジャンル）。0003 の「まずコンサート・ミュージカル」は採らない。
- 期間: **今日から 180 日後まで**の公演期間と重なる公演（人間の決定、2026-11-05）。1回の照会は最大 31 日なので、31 日ずつに分けて呼ぶ。それより先に始まる公演は、180 日以内になってから収集・表示される。
- 2回目以降は `afterdate`（前回の収集が成功した日）を付け、追加・変更された公演だけを取る。公演詳細はその公演だけ呼ぶ。施設詳細は、まだ持っていない施設だけ呼ぶ。
- 終わった公演を、期間をさかのぼってまとめて収集することはしない（人間の決定、2026-11-05）。ただし、人気順位・受賞作の結果に、まだ持っていない公演 ID があれば、その公演の詳細と施設だけを取る（人気順位には終わった公演も出るため。F-09 ④、F-29 ⑤）。
- 公演が終わったかどうかは公演期間と今日の日付で判断する（KOPIS の状態の値は使わない）。終わった公演のデータは消さない（F-09 ②）。

### 3. 人気順位の期間（F-29 ④、F-33 ②。R-48・R-52）

期間は**暦の日・暦の週（月曜〜日曜）・暦の月**で区切り、**終わった直近の期間**を「現在の期間」として表示する。日付は Asia/Seoul で数える。

| 期間 | 現在の期間（表示する順位） | 直前の期間（F-33 ② で比べる） | 例: 2026-11-05（木）に収集したとき |
|---|---|---|---|
| 日次 | 前日 | 前々日 | 現在 11/4、直前 11/3 |
| 週次 | 先週の月曜〜日曜 | その前の週の月曜〜日曜 | 現在 10/26〜11/1、直前 10/19〜10/25 |
| 月次 | 先月の1日〜末日 | 先々月の1日〜末日 | 現在 10/1〜10/31、直前 9/1〜9/30 |

- KOPIS の照会: `boxoffice` の `stdate` に期間の初日、`eddate` に期間の末日を指定する。どの期間も 31 日以内なので、1期間 1回の照会で取れる（取れることは「注意点」の確認事項）。
- 毎日の収集で、その日から見た現在の期間と直前の期間の両方を、日次・週次・月次のすべてについて取り直す。週・月の途中の日も同じ期間を取り直して上書きする（収集に失敗した日があっても、次に成功した日に埋まる）。
- ジャンル: 全体（`catecode` を指定しない）と、KOPIS のジャンル（公演の収集で使うジャンルの値と同じもの）ごと。
- 地域: ソウル（`area=11`）。
- **提供元が返したすべての行**を保存する（上位10位だけではない。非表示の公演を除いて繰り上げるため。F-29 ⑧、F-33 ⑩）。

### 4. 人気急上昇の順位の変化の計算方式（R-47、O-08）

**方式: 毎日、現在の期間と直前の期間の両方の順位を KOPIS から取得して保存し、保存した順位から計算する。**

- 同じ期間・同じジャンルの順位を取り直したときは上書きする（何度実行しても同じ結果になる）。
- 計算は、保存した順位と、**計算する時点の非表示の状態**を使って行う。管理者が公演を非表示にした・解除したとき、人気順位・人気急上昇にすぐ反映される（F-27 ②）。非表示にした時期の履歴は持たない。

**① 現在の順位: 非表示の公演を除いて振り直した順位を使う（R-54）。**
人気順位（F-29 ⑧）で表示する順位と同じ番号になる。

**② 直前の期間の上位10位: 非表示の公演を除いて振り直した上位10位を使う（R-56）。**
上昇幅は「振り直した直前の期間の順位 − 振り直した現在の期間の順位」で計算する（F-33 ⑨）。

**計算の手順**（期間の種類・ジャンルごと）:

1. 現在の期間の順位から非表示の公演を除き、1 から振り直す。上位10位を「対象」とする（R-51・R-54。元の11位以下から繰り上がって10位以内に入った公演も対象）。
2. 直前の期間の順位から非表示の公演を除き、1 から振り直す。上位10位を「直前の上位10位」とする（R-56）。
3. 対象のそれぞれについて:
   - 直前の上位10位にない → 「NEW」（F-33 ③、R-42-2）
   - 直前の上位10位にあり、直前の順位 − 現在の順位 > 0 → 上昇幅として表示する
   - 順位が同じ、または下がった → 表示しない
4. 並び順は F-33 ⑨（R-41）のとおり。「NEW」を先頭に現在の順位が高い順、その後に上昇幅の大きい順、同じなら現在の順位が高い順。
5. 表示は最大10件。対象が10件に満たなければ、ある分だけ表示する（F-33 ④⑩）。

**例**（週次・全体。2026-11-05 に見たとき、現在の期間は 10/26〜11/1、直前の期間は 10/19〜10/25。X は非表示）:

| 提供元の順位 | 現在の期間 | 直前の期間 |
|---|---|---|
| 1 | A | X |
| 2 | X | B |
| 3 | B | A |
| 4 | C | L |
| 5〜10 | D〜I | M〜R |
| 11 | K | C |

- 振り直した後: 現在は A=1, B=2, C=3, D〜I=4〜9, K=10（元の11位の K が繰り上がる）。直前は B=1, A=2, L〜R=3〜9, C=10（元の11位の C が繰り上がる）。
- 結果: A は 2→1 で「▲1」、B は 1→2 で下がったので表示しない、C は 10→3 で「▲7」、K は直前の上位10位にないので「NEW」（D〜I の扱いは略）。
- 提供元の順位のまま比べた場合は、C は直前の11位なので「NEW」になり、A は 3→1 で「▲2」になり、K は対象に入らない。非表示の公演 X があるだけで、ほかの公演の表示が変わってしまう。

**この方式を選ぶ理由**:

- 自分たちが保存した順位だけで計算する方式（企画書 8. の案）は、保存を始めた後に次の期間が終わるまで（月次では最大で約1か月）人気急上昇を表示できない。KOPIS から直前の期間も取れば、初日から表示できる。
- 振り直した順位どうしで比べると、利用者が人気順位（F-29）で見る番号と一致し、非表示の公演の有無で上昇幅や NEW がゆがまない（R-54・R-56 の決定と同じ）。

### 5. 受賞作・ロングラン・ジャンル別トレンド

- F-31: `prfawad` を、公演の収集と同じ地域・期間で毎日取り、公演 ID が一致する公演を「受賞歴あり」とする。
- F-32: オープンランかどうかは `openrun`。上演回数は、**その公演の開幕から現在までの累計**を表示する（R-49）。`prfstsPrfBy` の `prfdtcnt` を使う。
  - `prfdtcnt` が累計の値なら、その値を保存して表示する。
  - `prfdtcnt` が照会した期間の中の回数なら、公演の開幕日から今日までを 31 日ずつに分けて照会し、合計する。
  - どちらであるか、また開幕日までさかのぼって照会できるかは、実装の前に確かめる（「注意点」）。累計を得られないとわかった場合は、推測で別の値を出さず、作業を止めて人間に報告する。
- F-34: `boxStatsCate` で**前日までの直近 30 日**（F-34 ①「直近30日」。暦の月ではない）を取り、ジャンルの予約数 ÷ 全ジャンルの予約数で割合を計算する（30 日は 1回の照会の上限 31 日以内）。
  - ソウル（地域の指定）で絞れる場合は、ソウルの割合にする。
  - 絞れない場合は全国の割合にし、画面に「全国基準」と示す（R-50・R-55。X-08 の例外）。どちらの基準で集計したかを、割合と一緒に保存する（画面の表示に使う。文言と位置は 02 で決める）。

### 6. 呼び出しの制限・失敗への対応

- KOPIS は呼び出しの制限の具体的な数値を公開していない（開発ガイド v5.0）。呼び出しの間に間隔をあけ、失敗したときは間隔を広げて再試行する（具体的な値は 05 で決める）。
- 1日の呼び出し回数の目安: 順位 60 回（10 ジャンル × 3 期間 × 現在・直前）、ジャンル別統計 1 回、公演目録 6 期間 × ページ数、公演詳細は追加・変更された分（初回は全件 約 3,000 回）、公演別統計は F-32 の確認の結果による（期間の中の回数だった場合は、公演の数 × 開幕からの期間に比例して増える）。
- 失敗した日は、次の実行（翌日、または手動）でやり直す。公演は公演 ID、順位は期間・ジャンルで上書きするので、何度実行しても同じ結果になる。
- KOPIS は http のみで、認証キーが平文で送られる。**サーバーからだけ呼ぶ**（0003 と同じ）。キーは `.env` に置く。
- 画面に出典の表示が必要（例: `출처: (재)예술경영지원센터 공연예술통합전산망(www.kopis.or.kr)`）。場所は 02 で決める。

### 7. 実装の方式（ライブラリ）

- 呼び出しは Spring の HTTP クライアント（`RestClient`）で行う。
- 応答は XML なので、**Jackson の XML モジュール（`jackson-dataformat-xml`。バージョンは Spring Boot 4.1 の依存関係管理に従う）を追加する**。これは新しいライブラリの追加であり、この ADR の採用をもって導入を認める。

### この ADR で決めないこと

- 公演がどの区にあるかの判定方法（R-21）、公演詳細に示す順位の期間・ジャンル（O-01）: 基本設計の 02・03 などで決める。
- バッチの実行時刻・順番・再試行の値: 05 で決める。日付が変わってからその日の収集が終わるまでの間に、どの期間の順位を表示するか（保存済みの期間をそのまま出すかなど）も、05・03 で扱う。
- 保存のテーブル: db-designer が 04 で決める。

## 検討した選択肢

### 人気急上昇の計算方式（O-08）

| 選択肢 | 判断 |
|---|---|
| A. 自分たちが毎日保存した現在の順位だけを使う（企画書 8. の案） | 保存を始めた後に次の期間が終わるまで表示できない（月次は最大で約1か月）。保存に失敗した期間があると直前の期間が欠ける |
| **B. 毎日、現在と直前の期間の両方を KOPIS から取得・保存し、保存した順位で計算する** | **採用を提案。** 初日から計算でき、取り直せば欠けも埋まる。呼び出しは1日 30 回増えるだけ |
| C. 画面を開くたびに KOPIS を呼ぶ | 呼び出しが利用者の数に比例して増え、KOPIS の制限に触れるおそれがある。KOPIS が http のみで、キーをブラウザに出せない |

### ① 現在の順位・② 直前の上位10位での非表示の扱い

| 選択肢 | 判断 |
|---|---|
| **振り直した順位どうしで比べる（①振り直す、②除く）** | **採用を提案**（R-54・R-56 の決定と同じ）。F-29 の表示と一致し、非表示の公演でほかの公演の結果がゆがまない |
| 提供元の順位どうしで比べる（①提供元、②除かない） | 上昇幅は提供元の値のまま安定するが、利用者が F-29 で見る番号と合わない。非表示の公演が直前にあると、直前の11位が「NEW」になるなど、見えている順位と矛盾する |
| ①振り直す、②除かない（混在） | 比べる基準が両側で違い、非表示の公演が1件あるだけで上昇幅がずれる |

### 期間の区切り

| 選択肢 | 判断 |
|---|---|
| **暦の日・暦の週（月〜日）・暦の月の、終わった直近の期間** | **採用を提案**（人間の決定 R-48・R-52）。「先週」「先月」の言葉どおりで、終わった期間の順位なので、期間の途中で順位が変わらない。月の初めでも先月の順位を出し続けるため、月次は最大で約1か月前の期間の順位になる（要件として受け入れる） |
| 前日までの直近の期間（7 日・30 日） | 毎日更新され、比べる期間の長さがそろうが、R-48・R-52 と合わない。最初の提案ではこちらを挙げたが、採らない |

## 結果（良い点・注意点）

### 費用（月0円の範囲か）

| 項目 | 内容 |
|---|---|
| 無料枠 | KOPIS Open API は無料（料金なし） |
| カード登録 | 不要（kopis.or.kr で認証キーを申請。1人1つ） |
| 上限を超えたとき | 呼び出しの制限を超えると利用が止められることがある（数値は非公開）。課金はない |
| 上限・アラートの設定 | 課金がないため予算アラートは不要。呼び出しの間隔と再試行の上限をアプリ側で設定する（05） |

### 良い点

- 統計・評判の機能（F-29, F-31〜F-34）を、追加のサービスなしに KOPIS だけで作れる。
- 人気急上昇を初日から表示でき、何度実行しても同じ結果になる。

### 注意点（実装の前に開発ガイド v5.0 と実際の呼び出しで確かめること）

- `boxoffice` の期間の指定方法:
  - `stdate`・`eddate` に暦の週（月〜日、7 日）・暦の月（28〜31 日）を指定して、その期間を集計した順位が返るか。
  - 開発ガイドで「必須」とされる `date` の扱い。期間の種類（日・週・月）を指定する別の変数があるか。ある場合は、KOPIS の週の区切り（月曜始まりか）が R-48 と合うか。
  - 過去の期間をどこまで照会できるか（直前の期間として、先々月の1日まで、最大で約 62 日前を照会する）。
  - 前日の分の順位が、何時ごろから照会できるようになるか（バッチの実行時刻を決めるため。05）。
- `boxoffice` が1回に返す行数（上位何位まで返すか）。非表示の公演を除いて10件にするには、10件より多く返る必要がある。
- `boxStatsCate` を地域（ソウル）で絞れるか。絞れなければ全国の割合を「全国基準」として表示する（R-50。上の 5.）。
- `prfstsPrfBy` の `prfdtcnt` が累計か、照会した期間の中の回数か。期間の中の回数なら、開幕日までさかのぼって照会できるか、照会の条件（期間の上限、地域、ページ）。累計を得られない場合は作業を止めて人間に報告する（上の 5.）。
- `prfawad` の照会の条件（期間の上限、地域、ページ）。
- ジャンルの値（共通コードの一覧 `kopis_openapi_code_v3.7` はまだ取得していない）。

### 人間が決めたこと（2026-11-05。最初の提案の「未決」）

| 最初の提案での未決 | 決定 |
|---|---|
| F-32 ② の「上演回数」がどの期間の回数か | 開幕から現在までの累計（R-49） |
| F-34 をソウルに絞れない場合 | 全国の割合を表示し「全国基準」と示す。X-08 の例外（R-50・R-55）。「直近30日」は変わらない |
| 人気急上昇の「対象」を現在の期間の上位10位と読んでよいか | 現在の期間の上位10位だけ。非表示の公演を除いて振り直した後の上位10位で、繰り上がった公演も含む（R-51・R-54） |
| 直前の期間の上位10位でも非表示の公演を除くか、上昇幅をどの順位で計算するか | 除いて振り直す。上昇幅は振り直した順位どうし（R-56） |
| 公演の収集を「今日から 180 日後まで」にしてよいか | それでよい。終わった公演を別に集めることはしない |
| 週次・月次を「前日までの 7 日・30 日」にしてよいか | 採らない。暦の日・週（月〜日）・月の、終わった直近の期間にする（R-48・R-52） |

- 날짜: 2026-11-05
- 상태: 채택(2026-11-05, 사람이 결정)
- 대체: **0003을 대체한다**(0003의 "대상은 우선 콘서트·뮤지컬"을 전 장르로 넓히고 통계·평판 데이터를 더한다. 0003의 물품보관함 항목은 0009에서 다룬다). 0003의 상태는 "대체됨(→ 0008)"

- 공연 정보는 공개 데이터에서 하루 1번 자동 수집한다(F-08). 전 장르(F-08 ③), 서울만(F-08 ④).

#### 2. 공연 수집 범위 (F-08)

- 지역: 서울(`signgucode=11`).
- 장르: 지정하지 않는다(전 장르). 0003의 "우선 콘서트·뮤지컬"은 따르지 않는다.
- 기간: **오늘부터 180일 후까지**의 공연 기간과 겹치는 공연(사람의 결정, 2026-11-05). 1번 조회는 최대 31일이므로 31일씩 나눠 부른다. 그보다 뒤에 시작하는 공연은 180일 이내가 되고 나서 수집·표시된다.
- 두 번째부터는 `afterdate`(지난 수집이 성공한 날)를 붙여 추가·변경된 공연만 가져온다. 공연상세는 그 공연만 부른다. 시설상세는 아직 없는 시설만 부른다.
- 끝난 공연을 기간을 거슬러 올라가 한꺼번에 수집하지는 않는다(사람의 결정, 2026-11-05). 단, 인기 순위·수상작 결과에 아직 없는 공연 ID가 있으면 그 공연의 상세와 시설만 가져온다(인기 순위에는 끝난 공연도 나오기 때문. F-09 ④, F-29 ⑤).
- 공연이 끝났는지는 공연 기간과 오늘 날짜로 판단한다(KOPIS 상태 값은 쓰지 않는다). 끝난 공연 데이터는 지우지 않는다(F-09 ②).

#### 3. 인기 순위의 기간 (F-29 ④, F-33 ②. R-48·R-52)

기간은 **달력의 날·달력의 주(월요일~일요일)·달력의 월**로 나누고, **끝난 가장 최근 기간**을 "현재 기간"으로 표시한다. 날짜는 Asia/Seoul 기준으로 센다.

| 기간 | 현재 기간(표시하는 순위) | 직전 기간(F-33 ②에서 비교) | 예: 2026-11-05(목)에 수집했을 때 |
|---|---|---|---|
| 일간 | 전날 | 전전날 | 현재 11/4, 직전 11/3 |
| 주간 | 지난주 월요일~일요일 | 그 앞 주 월요일~일요일 | 현재 10/26~11/1, 직전 10/19~10/25 |
| 월간 | 지난달 1일~말일 | 지지난달 1일~말일 | 현재 10/1~10/31, 직전 9/1~9/30 |

- KOPIS 조회: `boxoffice`의 `stdate`에 기간 첫날, `eddate`에 기간 마지막 날을 지정한다. 어느 기간이든 31일 이내이므로 기간 1개를 1번 조회로 가져올 수 있다(가져올 수 있는지는 "주의점"의 확인 사항).
- 매일 수집할 때, 그날에서 본 현재 기간과 직전 기간 둘 다를 일간·주간·월간 전부에 대해 다시 가져온다. 주·월 중간의 날에도 같은 기간을 다시 가져와 덮어쓴다(수집에 실패한 날이 있어도 다음에 성공한 날에 채워진다).
- 장르: 전체(`catecode` 미지정)와 KOPIS 장르(공연 수집에 쓰는 장르 값과 같은 것)별.
- 지역: 서울(`area=11`).
- **제공처가 돌려준 모든 행**을 저장한다(상위 10위만이 아니다. 숨긴 공연을 빼고 올려 채우기 위해. F-29 ⑧, F-33 ⑩).

#### 4. 인기 급상승 순위 변화 계산 방식 (R-47, O-08)

**방식: 매일 현재 기간과 직전 기간 둘 다의 순위를 KOPIS에서 가져와 저장하고, 저장한 순위로 계산한다.**

- 같은 기간·같은 장르의 순위를 다시 가져오면 덮어쓴다(몇 번 실행해도 같은 결과).
- 계산은 저장한 순위와 **계산하는 시점의 숨김 상태**로 한다. 관리자가 공연을 숨기거나 해제하면 인기 순위·인기 급상승에 바로 반영된다(F-27 ②). 숨긴 시기의 이력은 갖지 않는다.

**① 현재 순위: 숨긴 공연을 빼고 다시 매긴 순위를 쓴다(R-54).**
인기 순위(F-29 ⑧)에 보이는 순위와 같은 번호가 된다.

**② 직전 기간 상위 10위: 숨긴 공연을 빼고 다시 매긴 상위 10위를 쓴다(R-56).**
상승폭은 "다시 매긴 직전 기간 순위 − 다시 매긴 현재 기간 순위"로 계산한다(F-33 ⑨).

**계산 절차**(기간 종류·장르별):

1. 현재 기간 순위에서 숨긴 공연을 빼고 1부터 다시 매긴다. 상위 10위를 "대상"으로 한다(R-51·R-54. 원래 11위 이하에서 올라와 10위 안에 든 공연도 대상).
2. 직전 기간 순위에서 숨긴 공연을 빼고 1부터 다시 매긴다. 상위 10위를 "직전 상위 10위"로 한다(R-56).
3. 대상 각각에 대해:
   - 직전 상위 10위에 없음 → "NEW"(F-33 ③, R-42-2)
   - 직전 상위 10위에 있고, 직전 순위 − 현재 순위 > 0 → 상승폭으로 보여준다
   - 순위가 같거나 내려감 → 보여주지 않는다
4. 정렬은 F-33 ⑨(R-41)대로. "NEW"를 맨 앞에 현재 순위가 높은 순, 그 뒤에 상승폭이 큰 순, 같으면 현재 순위가 높은 순.
5. 최대 10건 표시. 대상이 10건 미만이면 있는 만큼 보여준다(F-33 ④⑩).

**예**(주간·전체. 2026-11-05에 봤을 때 현재 기간은 10/26~11/1, 직전 기간은 10/19~10/25. X는 숨긴 공연):

| 제공처 순위 | 현재 기간 | 직전 기간 |
|---|---|---|
| 1 | A | X |
| 2 | X | B |
| 3 | B | A |
| 4 | C | L |
| 5~10 | D~I | M~R |
| 11 | K | C |

- 다시 매긴 뒤: 현재는 A=1, B=2, C=3, D~I=4~9, K=10(원래 11위인 K가 올라온다). 직전은 B=1, A=2, L~R=3~9, C=10(원래 11위인 C가 올라온다).
- 결과: A는 2→1로 "▲1", B는 1→2로 내려가 보여주지 않음, C는 10→3으로 "▲7", K는 직전 상위 10위에 없어서 "NEW"(D~I의 처리는 생략).
- 제공처 순위 그대로 비교하면 C는 직전 11위라서 "NEW", A는 3→1로 "▲2"가 되고, K는 대상에 들지 않는다. 숨긴 공연 X가 있다는 것만으로 다른 공연의 표시가 바뀐다.

**이 방식을 고르는 이유**:

- 우리가 저장한 순위만으로 계산하는 방식(기획서 8.의 안)은 저장을 시작한 뒤 다음 기간이 끝날 때까지(월간은 최대 약 1개월) 인기 급상승을 보여줄 수 없다. KOPIS에서 직전 기간도 가져오면 첫날부터 보여줄 수 있다.
- 다시 매긴 순위끼리 비교하면 이용자가 인기 순위(F-29)에서 보는 번호와 일치하고, 숨긴 공연 여부로 상승폭이나 NEW가 비뚤어지지 않는다(R-54·R-56의 결정과 같음).

#### 5. 수상작·롱런·장르별 트렌드

- F-31: `prfawad`를 공연 수집과 같은 지역·기간으로 매일 가져와, 공연 ID가 일치하는 공연을 "수상 이력 있음"으로 한다.
- F-32: 오픈런 여부는 `openrun`. 상연 횟수는 **그 공연의 개막부터 현재까지의 누계**를 표시한다(R-49). `prfstsPrfBy`의 `prfdtcnt`를 쓴다.
  - `prfdtcnt`가 누계 값이면 그 값을 저장해 표시한다.
  - `prfdtcnt`가 조회한 기간 안의 횟수이면, 공연 개막일부터 오늘까지를 31일씩 나눠 조회해 합계를 낸다.
  - 어느 쪽인지, 또 개막일까지 거슬러 올라가 조회할 수 있는지는 구현 전에 확인한다("주의점"). 누계를 얻을 수 없다고 판명되면 추측으로 다른 값을 내지 말고 작업을 멈추고 사람에게 보고한다.
- F-34: `boxStatsCate`로 **전날까지 최근 30일**(F-34 ① "최근 30일". 달력의 월이 아님)을 가져와 장르 예매수 ÷ 전 장르 예매수로 비중을 계산한다(30일은 1번 조회 상한 31일 이내).
  - 서울(지역 지정)로 거를 수 있으면 서울 비중으로 한다.
  - 거를 수 없으면 전국 비중으로 하고, 화면에 "전국 기준"으로 표시한다(R-50·R-55. X-08의 예외). 어느 기준으로 집계했는지를 비중과 함께 저장한다(화면 표시에 쓴다. 문구와 위치는 02에서 정함).

#### 6. 호출 제한·실패 대응

- KOPIS는 호출 제한의 구체적인 수치를 공개하지 않는다(개발가이드 v5.0). 호출 사이에 간격을 두고, 실패하면 간격을 늘려 다시 시도한다(구체적인 값은 05에서 정함).
- 하루 호출 횟수 기준: 순위 60회(10장르 × 3기간 × 현재·직전), 장르별 통계 1회, 공연목록 6기간 × 페이지 수, 공연상세는 추가·변경분(첫 수집은 전체 약 3,000회), 공연별 통계는 F-32 확인 결과에 따른다(기간 안의 횟수라면 공연 수 × 개막부터의 기간에 비례해 늘어난다).
- 실패한 날은 다음 실행(다음 날 또는 수동)에서 다시 한다. 공연은 공연 ID, 순위는 기간·장르로 덮어쓰므로 몇 번 실행해도 같은 결과가 된다.
- KOPIS는 http만 지원하고 인증키가 평문으로 전송된다. **서버에서만 부른다**(0003과 같음). 키는 `.env`에 둔다.
- 화면에 출처 표기가 필요하다(예: `출처: (재)예술경영지원센터 공연예술통합전산망(www.kopis.or.kr)`). 위치는 02에서 정한다.

#### 7. 구현 방식(라이브러리)

- 호출은 Spring HTTP 클라이언트(`RestClient`)로 한다.
- 응답이 XML이므로 **Jackson XML 모듈(`jackson-dataformat-xml`. 버전은 Spring Boot 4.1 의존성 관리를 따름)을 추가한다**. 새 라이브러리 추가이며, 이 ADR의 채택으로 도입을 허용한다.

#### 이 ADR에서 정하지 않는 것

- 공연이 어느 구에 있는지 판정하는 방법(R-21), 공연 상세에 보여줄 순위의 기간·장르(O-01): 기본설계 02·03 등에서 정한다.
- 배치 실행 시각·순서·재시도 값: 05에서 정한다. 날짜가 바뀐 뒤 그날의 수집이 끝날 때까지 어느 기간의 순위를 보여줄지(저장된 기간을 그대로 보여줄지 등)도 05·03에서 다룬다.
- 저장 테이블: db-designer가 04에서 정한다.

|---|---|
| A. 우리가 매일 저장한 현재 순위만 쓴다(기획서 8.의 안) | 저장을 시작한 뒤 다음 기간이 끝날 때까지 보여줄 수 없다(월간은 최대 약 1개월). 저장에 실패한 기간이 있으면 직전 기간이 빠진다 |
| **B. 매일 현재와 직전 기간 둘 다 KOPIS에서 가져와 저장하고, 저장한 순위로 계산한다** | **채택 제안.** 첫날부터 계산할 수 있고, 다시 가져오면 빠진 것도 채워진다. 호출은 하루 30회 늘 뿐이다 |
| C. 화면을 열 때마다 KOPIS를 부른다 | 호출이 이용자 수에 비례해 늘어 KOPIS 제한에 걸릴 수 있다. KOPIS가 http만 지원해 키를 브라우저에 노출할 수 없다 |

#### ① 현재 순위·② 직전 상위 10위에서 숨긴 공연 처리

| 선택지 | 판단 |
|---|---|
| **다시 매긴 순위끼리 비교(① 다시 매김, ② 뺀다)** | **채택 제안**(R-54·R-56의 결정과 같음). F-29 표시와 일치하고 숨긴 공연 때문에 다른 공연의 결과가 비뚤어지지 않는다 |
| 제공처 순위끼리 비교(① 제공처, ② 빼지 않음) | 상승폭은 제공처 값 그대로 안정적이지만, 이용자가 F-29에서 보는 번호와 맞지 않는다. 숨긴 공연이 직전에 있으면 직전 11위가 "NEW"가 되는 등 보이는 순위와 모순된다 |
| ① 다시 매김, ② 빼지 않음(혼합) | 비교 기준이 양쪽에서 달라, 숨긴 공연이 1건만 있어도 상승폭이 어긋난다 |

#### 기간 구분

| 선택지 | 판단 |
|---|---|
| **달력의 날·달력의 주(월~일)·달력의 월의, 끝난 가장 최근 기간** | **채택 제안**(사람의 결정 R-48·R-52). "지난주", "지난달"이라는 말 그대로이고, 끝난 기간의 순위라서 기간 도중에 순위가 바뀌지 않는다. 월초에도 지난달 순위를 계속 보여주므로 월간은 최대 약 1개월 전 기간의 순위가 된다(요건으로 받아들인다) |
| 전날까지의 최근 기간(7일·30일) | 매일 갱신되고 비교하는 기간 길이가 같지만, R-48·R-52와 맞지 않는다. 첫 제안에서는 이쪽을 올렸지만 쓰지 않는다 |

### 결과 (좋은 점·주의점)

#### 비용 (월 0원 범위인가)

| 항목 | 내용 |
|---|---|
| 무료 한도 | KOPIS Open API는 무료(요금 없음) |
| 카드 등록 | 불필요(kopis.or.kr에서 인증키 신청. 1인 1개) |
| 한도를 넘었을 때 | 호출 제한을 넘으면 이용이 중지될 수 있다(수치 비공개). 과금은 없다 |
| 상한·알림 설정 | 과금이 없으므로 예산 알림은 불필요. 호출 간격과 재시도 상한을 앱에서 설정한다(05) |

#### 좋은 점

- 통계·평판 기능(F-29, F-31~F-34)을 추가 서비스 없이 KOPIS만으로 만들 수 있다.
- 인기 급상승을 첫날부터 보여줄 수 있고, 몇 번 실행해도 같은 결과가 된다.

#### 주의점 (구현 전에 개발가이드 v5.0과 실제 호출로 확인할 것)

- `boxoffice`의 기간 지정 방법:
  - `stdate`·`eddate`에 달력의 주(월~일, 7일)·달력의 월(28~31일)을 지정해서 그 기간을 집계한 순위가 오는지.
  - 개발가이드에서 "필수"로 된 `date`의 처리. 기간 종류(일·주·월)를 지정하는 다른 변수가 있는지. 있다면 KOPIS의 주 구분(월요일 시작인지)이 R-48과 맞는지.
  - 과거 기간을 어디까지 조회할 수 있는지(직전 기간으로 지지난달 1일까지, 최대 약 62일 전을 조회한다).
  - 전날 분의 순위를 몇 시쯤부터 조회할 수 있는지(배치 실행 시각을 정하기 위해. 05).
- `boxoffice`가 한 번에 돌려주는 행 수(몇 위까지 돌려주는지). 숨긴 공연을 빼고 10건을 채우려면 10건보다 많이 와야 한다.
- `boxStatsCate`를 지역(서울)으로 거를 수 있는지. 거를 수 없으면 전국 비중을 "전국 기준"으로 표시한다(R-50. 위 5.).
- `prfstsPrfBy`의 `prfdtcnt`가 누계인지, 조회한 기간 안의 횟수인지. 기간 안의 횟수라면 개막일까지 거슬러 조회할 수 있는지, 조회 조건(기간 상한, 지역, 페이지). 누계를 얻을 수 없으면 작업을 멈추고 사람에게 보고한다(위 5.).
- `prfawad`의 조회 조건(기간 상한, 지역, 페이지).
- 장르 값(공통코드 목록 `kopis_openapi_code_v3.7`은 아직 받지 않음).

#### 사람이 정한 것 (2026-11-05. 첫 제안의 "미결")

| 첫 제안의 미결 | 결정 |
|---|---|
| F-32 ② "상연 횟수"가 어느 기간의 횟수인지 | 개막부터 현재까지의 누계(R-49) |
| F-34를 서울로 거를 수 없는 경우 | 전국 비중을 표시하고 "전국 기준"으로 나타낸다. X-08의 예외(R-50·R-55). "최근 30일"은 바뀌지 않는다 |
| 인기 급상승의 "대상"을 현재 기간 상위 10위로 읽어도 되는지 | 현재 기간 상위 10위뿐. 숨긴 공연을 빼고 다시 매긴 뒤의 상위 10위이며, 올라온 공연도 포함(R-51·R-54) |
| 직전 기간 상위 10위에서도 숨긴 공연을 빼는지, 상승폭을 어느 순위로 계산하는지 | 빼고 다시 매긴다. 상승폭은 다시 매긴 순위끼리(R-56) |
| 공연 수집을 "오늘부터 180일 후까지"로 해도 되는지 | 그렇게 한다. 끝난 공연을 따로 모으지 않는다 |
| 주간·월간을 "전날까지 7일·30일"로 해도 되는지 | 쓰지 않는다. 달력의 날·주(월~일)·월의 끝난 가장 최근 기간으로 한다(R-48·R-52) |

이 ADR에 사람의 판단을 기다리는 미결은 남아 있지 않다. 남은 것은 위 "주의점"의, 구현 전에 KOPIS로 확인할 사항이다.

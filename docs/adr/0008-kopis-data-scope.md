# 0008. KOPIS Open API のデータ範囲と、人気急上昇の順位の変化の計算方式

- 日付: 2026-11-05
- 状態: 提案
- 置き換え: **0003 を置き換える提案**（0003 の「対象はまずコンサート・ミュージカル」を全ジャンルに広げ、統計・評判のデータを加える。0003 のコインロッカーの項は 0009 で扱う）。0003 の状態は、人間が採用を決めるまで「提案」のまま変えない
- 関係する要件: F-01〜F-04, F-08, F-09, F-29, F-31〜F-34（U-15, R-47, O-08）

## 背景

- 公演情報は公開データから1日1回自動で収集する（F-08）。全ジャンル（F-08 ③）、ソウルだけ（F-08 ④）。
- 統計・評判の機能（F-29, F-31〜F-34）のデータの出どころを決める必要がある（U-15）。企画書 8. に、PM が KOPIS 開発ガイド v5.0 で確認した候補がある。
- 人気急上昇（F-33）の順位の変化の計算方式（R-47、O-08）を決める。あわせて Issue #14 の次の2つを決める。
  - ① R-41 の「現在の順位」は、提供元の順位か、非表示の公演を除いて振り直した順位か
  - ② 直前の期間の上位10位を決めるとき、非表示の公演を除くか
- 0003 は「対象はまずコンサート・ミュージカル」としており、全ジャンルの要件（F-08 ③）と合わない。

## 決定

### 1. 使う KOPIS のサービス

| 要件 | KOPIS のサービス | 使う項目 |
|---|---|---|
| F-01〜F-04, F-08, F-09（公演・会場） | 公演目録 `pblprfr` → 公演詳細 `pblprfr/{mt20id}` → 公演施設詳細 `prfplc/{mt10id}` | 公演 ID `mt20id`、公演名、期間、ジャンル、状態、出演者、予約先 `relates`、施設 ID `mt10id`、会場の緯度・経度 `la` `lo`、住所 |
| F-29（人気順位）, F-33（人気急上昇） | 予約状況板 `boxoffice` | 順位 `rnum`、公演 ID `mt20id` |
| F-31（受賞作バッジ） | 受賞作目録 `prfawad` | 公演 ID、`awards` |
| F-32（ロングラン・オープンラン） | 公演目録・公演詳細の `openrun`、公演別統計 `prfstsPrfBy` の上演回数 `prfdtcnt` | — |
| F-34（ジャンル別トレンド） | ジャンル別予約統計 `boxStatsCate` | ジャンルごとの予約数 |

F-30（評価）は KOPIS にデータがないため、自分たちのレビューで計算する（KOPIS は使わない）。

### 2. 公演の収集の範囲（F-08）

- 地域: ソウル（`signgucode=11`）。
- ジャンル: 指定しない（全ジャンル）。0003 の「まずコンサート・ミュージカル」は採らない。
- 期間: **今日から 180 日後まで**の公演期間と重なる公演。1回の照会は最大 31 日なので、31 日ずつに分けて呼ぶ。
- 2回目以降は `afterdate`（前回の収集が成功した日）を付け、追加・変更された公演だけを取る。公演詳細はその公演だけ呼ぶ。施設詳細は、まだ持っていない施設だけ呼ぶ。
- 人気順位・受賞作の結果に、まだ持っていない公演 ID があれば、その公演の詳細と施設も取る（終わった公演も人気順位に出るため。F-09 ④）。
- 公演が終わったかどうかは公演期間と今日の日付で判断する（KOPIS の状態の値は使わない）。終わった公演のデータは消さない（F-09 ②）。

### 3. 人気順位の期間（F-29 ④）

期間は**前日までの直近の期間**で区切る（1日1回の収集の時点で、前日までのデータで決まった順位を使う）。

| 期間 | 現在の期間 | 直前の期間（F-33 ②） |
|---|---|---|
| 日次 | 前日（1日） | 2日前（1日） |
| 週次 | 前日までの 7 日 | その前の 7 日（8〜14 日前） |
| 月次 | 前日までの 30 日 | その前の 30 日（31〜60 日前） |

- ジャンル: 全体（`catecode` を指定しない）と、KOPIS のジャンル（公演の収集で使うジャンルの値と同じもの）ごと。
- 地域: ソウル（`area=11`）。
- **提供元が返したすべての行**を保存する（上位10位だけではない。非表示の公演を除いて繰り上げるため。F-29 ⑧）。

### 4. 人気急上昇の順位の変化の計算方式（R-47、O-08）

**方式: 毎日、現在の期間と直前の期間の両方の順位を KOPIS から取得して保存し、保存した順位から計算する。**

- 同じ期間・同じジャンルの順位を取り直したときは上書きする（何度実行しても同じ結果になる）。
- 計算は、保存した順位と、**計算する時点の非表示の状態**を使って行う。管理者が公演を非表示にした・解除したとき、人気順位・人気急上昇にすぐ反映される（F-27 ②）。非表示にした時期の履歴は持たない。

**① 現在の順位: 非表示の公演を除いて振り直した順位を使う。**
人気順位（F-29 ⑧）で表示する順位と同じ番号になる。

**② 直前の期間の上位10位: 非表示の公演を除いて振り直した上位10位を使う。**
上昇幅も、振り直した直前の順位と振り直した現在の順位の差で計算する。

**計算の手順**（期間・ジャンルごと）:

1. 現在の期間の順位から非表示の公演を除き、1 から振り直す。上位10位を「対象」とする。
2. 直前の期間の順位から非表示の公演を除き、1 から振り直す。上位10位を「直前の上位10位」とする。
3. 対象のそれぞれについて:
   - 直前の上位10位にない → 「NEW」（F-33 ③、R-42-2）
   - 直前の上位10位にあり、直前の順位 − 現在の順位 > 0 → 上昇幅として表示する
   - 順位が同じ、または下がった → 表示しない
4. 並び順は F-33 ⑨（R-41）のとおり。「NEW」を先頭に現在の順位が高い順、その後に上昇幅の大きい順、同じなら現在の順位が高い順。
5. 表示は最大10件。対象が10件に満たなければ、ある分だけ表示する（F-33 ④⑩）。

**要件の読み方（人間に確認したい）**: F-33 ④ の「上位10位まで」と R-42-2 の「直前の期間の上位10位」から、人気急上昇の「対象」は**現在の期間の上位10位**と読んだ。現在の11位以下を対象にすると、直前の上位10位にない公演がすべて「NEW」になり、NEW を先頭に置く並び順（F-33 ⑨）では上昇した公演がほとんど表示されなくなるため。

**例**（週次・全体。H は非表示）:

| 提供元の順位 | 現在の期間 | 直前の期間 |
|---|---|---|
| 1 | A | H |
| 2 | H | B |
| 3 | B | A |
| 4 | C | D〜J（略） |
| … | … | … |
| 11 | K | C |

- 振り直した後: 現在は A=1, B=2, C=3 …、直前は B=1, A=2 …, C=10（11位だった C が繰り上がる）。
- 結果: A は 2→1 で「▲1」、B は 1→2 で下がったので表示しない、C は 10→3 で「▲7」。
- 提供元の順位のまま比べた場合は、C は直前の11位なので「NEW」になり、A は 3→1 で「▲2」になる。非表示の公演 H があるだけで、ほかの公演の表示が変わってしまう。

**この方式を選ぶ理由**:

- 自分たちが保存した順位だけで計算する方式（企画書 8. の案）は、保存を始めてから直前の期間がそろうまで（月次では 60 日）人気急上昇を表示できない。KOPIS から直前の期間も取れば、初日から表示できる。
- 振り直した順位どうしで比べると、利用者が人気順位（F-29）で見る番号と一致し、非表示の公演の有無で上昇幅や NEW がゆがまない。

### 5. 受賞作・ロングラン・ジャンル別トレンド

- F-31: `prfawad` を、公演の収集と同じ地域・期間で毎日取り、公演 ID が一致する公演を「受賞歴あり」とする。
- F-32: オープンランかどうかは `openrun`。上演回数は `prfstsPrfBy` の `prfdtcnt` を使う。**何の期間の上演回数か（開幕からの累計か）は要件に書かれていない**ため、人間に確認する（下の「未決」）。
- F-34: `boxStatsCate` で前日までの 30 日（F-29 の月次と同じ期間）を取り、ジャンルの予約数 ÷ 全ジャンルの予約数で割合を計算する。

### 6. 呼び出しの制限・失敗への対応

- KOPIS は呼び出しの制限の具体的な数値を公開していない（開発ガイド v5.0）。呼び出しの間に間隔をあけ、失敗したときは間隔を広げて再試行する（具体的な値は 05 で決める）。
- 1日の呼び出し回数の目安: 順位 60 回（10 ジャンル × 3 期間 × 現在・直前）、ジャンル別統計 1 回、公演目録 6 期間 × ページ数、公演詳細は追加・変更された分（初回は全件 約 3,000 回）。
- 失敗した日は、次の実行（翌日、または手動）でやり直す。公演は公演 ID、順位は期間・ジャンルで上書きするので、何度実行しても同じ結果になる。
- KOPIS は http のみで、認証キーが平文で送られる。**サーバーからだけ呼ぶ**（0003 と同じ）。キーは `.env` に置く。
- 画面に出典の表示が必要（例: `출처: (재)예술경영지원센터 공연예술통합전산망(www.kopis.or.kr)`）。場所は 02 で決める。

### 7. 実装の方式（ライブラリ）

- 呼び出しは Spring の HTTP クライアント（`RestClient`）で行う。
- 応答は XML なので、**Jackson の XML モジュール（`jackson-dataformat-xml`。バージョンは Spring Boot 4.1 の依存関係管理に従う）を追加する**。これは新しいライブラリの追加であり、この ADR の採用をもって導入を認める。

### この ADR で決めないこと

- 公演がどの区にあるかの判定方法（R-21）、公演詳細に示す順位の期間・ジャンル（O-01）: 基本設計の 02・03 などで決める。
- バッチの実行時刻・順番・再試行の値: 05 で決める。
- 保存のテーブル: db-designer が 04 で決める。

## 検討した選択肢

### 人気急上昇の計算方式（O-08）

| 選択肢 | 判断 |
|---|---|
| A. 自分たちが毎日保存した現在の順位だけを使う（企画書 8. の案） | 履歴がそろうまで表示できない（月次は 60 日）。保存に失敗した日があると直前の期間が欠ける |
| **B. 毎日、現在と直前の期間の両方を KOPIS から取得・保存し、保存した順位で計算する** | **採用を提案。** 初日から計算でき、取り直せば欠けも埋まる。呼び出しは1日 30 回増えるだけ |
| C. 画面を開くたびに KOPIS を呼ぶ | 呼び出しが利用者の数に比例して増え、KOPIS の制限に触れるおそれがある。KOPIS が http のみで、キーをブラウザに出せない |

### ① 現在の順位・② 直前の上位10位での非表示の扱い

| 選択肢 | 判断 |
|---|---|
| **振り直した順位どうしで比べる（①振り直す、②除く）** | **採用を提案。** F-29 の表示と一致し、非表示の公演でほかの公演の結果がゆがまない |
| 提供元の順位どうしで比べる（①提供元、②除かない） | 上昇幅は提供元の値のまま安定するが、利用者が F-29 で見る番号と合わない。非表示の公演が直前にあると、直前の11位が「NEW」になるなど、見えている順位と矛盾する |
| ①振り直す、②除かない（混在） | 比べる基準が両側で違い、非表示の公演が1件あるだけで上昇幅がずれる |

### 期間の区切り

| 選択肢 | 判断 |
|---|---|
| **前日までの直近の期間（7 日・30 日）** | **採用を提案。** 毎日更新され、比べる期間の長さがそろう。F-34 の「直近30日」とも合う |
| 暦の週（月〜日）・暦の月 | 「前週」「前月」の言葉には近いが、月の初めは前月のデータになり、最大 1 か月古い順位を出し続ける |

## 結果（良い点・注意点）

### 費用（月0円の範囲か）

| 項目 | 内容 |
|---|---|
| 無料枠 | KOPIS Open API は無料（料金なし） |
| カード登録 | 不要（kopis.or.kr で認証キーを申請。1人1つ） |
| 上限を超えたとき | 呼び出しの制限を超えると利用が止められることがある（数値は非公開）。課金はない |
| 上限・アラートの設定 | 課金がないため予算アラートは不要。呼び出しの間隔と再試行の上限をアプリ側で設定する（05） |

### 良い点

- 統計・評判の機能（F-29, F-31〜F-34）を、追加のサービスなしに KOPIS だけで作れる。
- 人気急上昇を初日から表示でき、何度実行しても同じ結果になる。

### 注意点（実装の前に開発ガイド v5.0 と実際の呼び出しで確かめること）

- `boxoffice` の期間の指定方法（`stdate`・`eddate` で任意の期間を指定できるか。開発ガイドで「必須」とされる `date` の扱い）と、過去の期間を照会できるか。
- `boxoffice` が1回に返す行数（上位何位まで返すか）。非表示の公演を除いて10件にするには、10件より多く返る必要がある。
- `boxStatsCate` を地域（ソウル）で絞れるか。**絞れない場合は全国の割合になる**ため、人間に確認する。
- `prfawad`・`prfstsPrfBy` の照会の条件（期間の上限、地域、ページ）と、`prfdtcnt` が期間内の回数か累計か。
- ジャンルの値（共通コードの一覧 `kopis_openapi_code_v3.7` はまだ取得していない）。

### 未決（人間に確認したいこと）

- F-32 ②「上演回数」がどの期間の回数か（開幕からの累計 / 直近の期間など）。要件に書かれていない。
- F-34 が「ソウルの」割合であるべきか（`boxStatsCate` で地域を絞れない場合）。
- 人気急上昇の「対象」を現在の期間の上位10位と読んでよいか（上の「要件の読み方」）。
- 公演の収集を「今日から 180 日後まで」にしてよいか（それより先に始まる公演は、180 日以内になってから表示される）。
- 週次・月次を「前日までの 7 日・30 日」（暦の週・月ではない）としてよいか。F-33 ② の「前週」「前月」を「その前の 7 日・30 日」と読んでいる。

## 한국어

### 0008. KOPIS Open API 데이터 범위와 인기 급상승 순위 변화 계산 방식

- 날짜: 2026-11-05
- 상태: 제안
- 대체: **0003을 대체하는 제안**(0003의 "대상은 우선 콘서트·뮤지컬"을 전 장르로 넓히고 통계·평판 데이터를 더한다. 0003의 물품보관함 항목은 0009에서 다룬다). 0003의 상태는 사람이 채택을 정할 때까지 "제안" 그대로 둔다
- 관련 요건: F-01~F-04, F-08, F-09, F-29, F-31~F-34 (U-15, R-47, O-08)

### 배경

- 공연 정보는 공개 데이터에서 하루 1번 자동 수집한다(F-08). 전 장르(F-08 ③), 서울만(F-08 ④).
- 통계·평판 기능(F-29, F-31~F-34)의 데이터 출처를 정해야 한다(U-15). 기획서 8.에 PM이 KOPIS 개발가이드 v5.0에서 확인한 후보가 있다.
- 인기 급상승(F-33)의 순위 변화 계산 방식(R-47, O-08)을 정한다. 함께 Issue #14의 다음 두 가지를 정한다.
  - ① R-41의 "현재 순위"는 제공처 순위인가, 숨긴 공연을 빼고 다시 매긴 순위인가
  - ② 직전 기간 상위 10위를 정할 때 숨긴 공연을 빼는가
- 0003은 "대상은 우선 콘서트·뮤지컬"이라고 해서 전 장르 요건(F-08 ③)과 맞지 않는다.

### 결정

#### 1. 쓰는 KOPIS 서비스

| 요건 | KOPIS 서비스 | 쓰는 항목 |
|---|---|---|
| F-01~F-04, F-08, F-09(공연·공연장) | 공연목록 `pblprfr` → 공연상세 `pblprfr/{mt20id}` → 공연시설상세 `prfplc/{mt10id}` | 공연 ID `mt20id`, 공연명, 기간, 장르, 상태, 출연진, 예매처 `relates`, 시설 ID `mt10id`, 공연장 위도·경도 `la` `lo`, 주소 |
| F-29(인기 순위), F-33(인기 급상승) | 예매상황판 `boxoffice` | 순위 `rnum`, 공연 ID `mt20id` |
| F-31(수상작 뱃지) | 수상작 목록 `prfawad` | 공연 ID, `awards` |
| F-32(롱런·오픈런) | 공연목록·공연상세의 `openrun`, 공연별 통계 `prfstsPrfBy`의 상연 횟수 `prfdtcnt` | — |
| F-34(장르별 트렌드) | 장르별 예매통계 `boxStatsCate` | 장르별 예매수 |

F-30(평점)은 KOPIS에 데이터가 없으므로 우리 리뷰로 계산한다(KOPIS는 쓰지 않음).

#### 2. 공연 수집 범위 (F-08)

- 지역: 서울(`signgucode=11`).
- 장르: 지정하지 않는다(전 장르). 0003의 "우선 콘서트·뮤지컬"은 따르지 않는다.
- 기간: **오늘부터 180일 후까지**의 공연 기간과 겹치는 공연. 1번 조회는 최대 31일이므로 31일씩 나눠 부른다.
- 두 번째부터는 `afterdate`(지난 수집이 성공한 날)를 붙여 추가·변경된 공연만 가져온다. 공연상세는 그 공연만 부른다. 시설상세는 아직 없는 시설만 부른다.
- 인기 순위·수상작 결과에 아직 없는 공연 ID가 있으면 그 공연의 상세와 시설도 가져온다(끝난 공연도 인기 순위에 나오기 때문. F-09 ④).
- 공연이 끝났는지는 공연 기간과 오늘 날짜로 판단한다(KOPIS 상태 값은 쓰지 않는다). 끝난 공연 데이터는 지우지 않는다(F-09 ②).

#### 3. 인기 순위의 기간 (F-29 ④)

기간은 **전날까지의 최근 기간**으로 나눈다(하루 1번 수집 시점에 전날까지의 데이터로 정해진 순위를 쓴다).

| 기간 | 현재 기간 | 직전 기간 (F-33 ②) |
|---|---|---|
| 일간 | 전날(1일) | 2일 전(1일) |
| 주간 | 전날까지 7일 | 그 앞 7일(8~14일 전) |
| 월간 | 전날까지 30일 | 그 앞 30일(31~60일 전) |

- 장르: 전체(`catecode` 미지정)와 KOPIS 장르(공연 수집에 쓰는 장르 값과 같은 것)별.
- 지역: 서울(`area=11`).
- **제공처가 돌려준 모든 행**을 저장한다(상위 10위만이 아니다. 숨긴 공연을 빼고 올려 채우기 위해. F-29 ⑧).

#### 4. 인기 급상승 순위 변화 계산 방식 (R-47, O-08)

**방식: 매일 현재 기간과 직전 기간 둘 다의 순위를 KOPIS에서 가져와 저장하고, 저장한 순위로 계산한다.**

- 같은 기간·같은 장르의 순위를 다시 가져오면 덮어쓴다(몇 번 실행해도 같은 결과).
- 계산은 저장한 순위와 **계산하는 시점의 숨김 상태**로 한다. 관리자가 공연을 숨기거나 해제하면 인기 순위·인기 급상승에 바로 반영된다(F-27 ②). 숨긴 시기의 이력은 갖지 않는다.

**① 현재 순위: 숨긴 공연을 빼고 다시 매긴 순위를 쓴다.**
인기 순위(F-29 ⑧)에 보이는 순위와 같은 번호가 된다.

**② 직전 기간 상위 10위: 숨긴 공연을 빼고 다시 매긴 상위 10위를 쓴다.**
상승폭도 다시 매긴 직전 순위와 다시 매긴 현재 순위의 차로 계산한다.

**계산 절차**(기간·장르별):

1. 현재 기간 순위에서 숨긴 공연을 빼고 1부터 다시 매긴다. 상위 10위를 "대상"으로 한다.
2. 직전 기간 순위에서 숨긴 공연을 빼고 1부터 다시 매긴다. 상위 10위를 "직전 상위 10위"로 한다.
3. 대상 각각에 대해:
   - 직전 상위 10위에 없음 → "NEW"(F-33 ③, R-42-2)
   - 직전 상위 10위에 있고, 직전 순위 − 현재 순위 > 0 → 상승폭으로 보여준다
   - 순위가 같거나 내려감 → 보여주지 않는다
4. 정렬은 F-33 ⑨(R-41)대로. "NEW"를 맨 앞에 현재 순위가 높은 순, 그 뒤에 상승폭이 큰 순, 같으면 현재 순위가 높은 순.
5. 최대 10건 표시. 대상이 10건 미만이면 있는 만큼 보여준다(F-33 ④⑩).

**요건 해석(사람에게 확인하고 싶음)**: F-33 ④의 "상위 10위까지"와 R-42-2의 "직전 기간 상위 10위"로부터, 인기 급상승의 "대상"을 **현재 기간 상위 10위**로 읽었다. 현재 11위 이하를 대상으로 하면 직전 상위 10위에 없던 공연이 모두 "NEW"가 되고, NEW를 맨 앞에 두는 정렬(F-33 ⑨)로는 상승한 공연이 거의 보이지 않게 되기 때문이다.

**예**(주간·전체. H는 숨긴 공연):

| 제공처 순위 | 현재 기간 | 직전 기간 |
|---|---|---|
| 1 | A | H |
| 2 | H | B |
| 3 | B | A |
| 4 | C | D~J(생략) |
| … | … | … |
| 11 | K | C |

- 다시 매긴 뒤: 현재는 A=1, B=2, C=3 …, 직전은 B=1, A=2 …, C=10(11위였던 C가 올라온다).
- 결과: A는 2→1로 "▲1", B는 1→2로 내려가 보여주지 않음, C는 10→3으로 "▲7".
- 제공처 순위 그대로 비교하면 C는 직전 11위라서 "NEW", A는 3→1로 "▲2"가 된다. 숨긴 공연 H가 있다는 것만으로 다른 공연의 표시가 바뀐다.

**이 방식을 고르는 이유**:

- 우리가 저장한 순위만으로 계산하는 방식(기획서 8.의 안)은 저장을 시작하고 직전 기간이 다 모일 때까지(월간은 60일) 인기 급상승을 보여줄 수 없다. KOPIS에서 직전 기간도 가져오면 첫날부터 보여줄 수 있다.
- 다시 매긴 순위끼리 비교하면 이용자가 인기 순위(F-29)에서 보는 번호와 일치하고, 숨긴 공연 여부로 상승폭이나 NEW가 비뚤어지지 않는다.

#### 5. 수상작·롱런·장르별 트렌드

- F-31: `prfawad`를 공연 수집과 같은 지역·기간으로 매일 가져와, 공연 ID가 일치하는 공연을 "수상 이력 있음"으로 한다.
- F-32: 오픈런 여부는 `openrun`. 상연 횟수는 `prfstsPrfBy`의 `prfdtcnt`를 쓴다. **어느 기간의 상연 횟수인지(개막부터 누계인지)는 요건에 적혀 있지 않으므로** 사람에게 확인한다(아래 "미결").
- F-34: `boxStatsCate`로 전날까지 30일(F-29 월간과 같은 기간)을 가져와 장르 예매수 ÷ 전 장르 예매수로 비율을 계산한다.

#### 6. 호출 제한·실패 대응

- KOPIS는 호출 제한의 구체적인 수치를 공개하지 않는다(개발가이드 v5.0). 호출 사이에 간격을 두고, 실패하면 간격을 늘려 다시 시도한다(구체적인 값은 05에서 정함).
- 하루 호출 횟수 기준: 순위 60회(10장르 × 3기간 × 현재·직전), 장르별 통계 1회, 공연목록 6기간 × 페이지 수, 공연상세는 추가·변경분(첫 수집은 전체 약 3,000회).
- 실패한 날은 다음 실행(다음 날 또는 수동)에서 다시 한다. 공연은 공연 ID, 순위는 기간·장르로 덮어쓰므로 몇 번 실행해도 같은 결과가 된다.
- KOPIS는 http만 지원하고 인증키가 평문으로 전송된다. **서버에서만 부른다**(0003과 같음). 키는 `.env`에 둔다.
- 화면에 출처 표기가 필요하다(예: `출처: (재)예술경영지원센터 공연예술통합전산망(www.kopis.or.kr)`). 위치는 02에서 정한다.

#### 7. 구현 방식(라이브러리)

- 호출은 Spring HTTP 클라이언트(`RestClient`)로 한다.
- 응답이 XML이므로 **Jackson XML 모듈(`jackson-dataformat-xml`. 버전은 Spring Boot 4.1 의존성 관리를 따름)을 추가한다**. 새 라이브러리 추가이며, 이 ADR의 채택으로 도입을 허용한다.

#### 이 ADR에서 정하지 않는 것

- 공연이 어느 구에 있는지 판정하는 방법(R-21), 공연 상세에 보여줄 순위의 기간·장르(O-01): 기본설계 02·03 등에서 정한다.
- 배치 실행 시각·순서·재시도 값: 05에서 정한다.
- 저장 테이블: db-designer가 04에서 정한다.

### 검토한 선택지

#### 인기 급상승 계산 방식 (O-08)

| 선택지 | 판단 |
|---|---|
| A. 우리가 매일 저장한 현재 순위만 쓴다(기획서 8.의 안) | 이력이 모일 때까지 보여줄 수 없다(월간은 60일). 저장에 실패한 날이 있으면 직전 기간이 빠진다 |
| **B. 매일 현재와 직전 기간 둘 다 KOPIS에서 가져와 저장하고, 저장한 순위로 계산한다** | **채택 제안.** 첫날부터 계산할 수 있고, 다시 가져오면 빠진 것도 채워진다. 호출은 하루 30회 늘 뿐이다 |
| C. 화면을 열 때마다 KOPIS를 부른다 | 호출이 이용자 수에 비례해 늘어 KOPIS 제한에 걸릴 수 있다. KOPIS가 http만 지원해 키를 브라우저에 노출할 수 없다 |

#### ① 현재 순위·② 직전 상위 10위에서 숨긴 공연 처리

| 선택지 | 판단 |
|---|---|
| **다시 매긴 순위끼리 비교(① 다시 매김, ② 뺀다)** | **채택 제안.** F-29 표시와 일치하고 숨긴 공연 때문에 다른 공연의 결과가 비뚤어지지 않는다 |
| 제공처 순위끼리 비교(① 제공처, ② 빼지 않음) | 상승폭은 제공처 값 그대로 안정적이지만, 이용자가 F-29에서 보는 번호와 맞지 않는다. 숨긴 공연이 직전에 있으면 직전 11위가 "NEW"가 되는 등 보이는 순위와 모순된다 |
| ① 다시 매김, ② 빼지 않음(혼합) | 비교 기준이 양쪽에서 달라, 숨긴 공연이 1건만 있어도 상승폭이 어긋난다 |

#### 기간 구분

| 선택지 | 판단 |
|---|---|
| **전날까지의 최근 기간(7일·30일)** | **채택 제안.** 매일 갱신되고 비교하는 기간 길이가 같다. F-34의 "최근 30일"과도 맞는다 |
| 달력 주(월~일)·달력 월 | "전주", "전월"이라는 말에는 가깝지만, 월초에는 전월 데이터가 되어 최대 1개월 묵은 순위를 계속 보여준다 |

### 결과 (좋은 점·주의점)

#### 비용 (월 0원 범위인가)

| 항목 | 내용 |
|---|---|
| 무료 한도 | KOPIS Open API는 무료(요금 없음) |
| 카드 등록 | 불필요(kopis.or.kr에서 인증키 신청. 1인 1개) |
| 한도를 넘었을 때 | 호출 제한을 넘으면 이용이 중지될 수 있다(수치 비공개). 과금은 없다 |
| 상한·알림 설정 | 과금이 없으므로 예산 알림은 불필요. 호출 간격과 재시도 상한을 앱에서 설정한다(05) |

#### 좋은 점

- 통계·평판 기능(F-29, F-31~F-34)을 추가 서비스 없이 KOPIS만으로 만들 수 있다.
- 인기 급상승을 첫날부터 보여줄 수 있고, 몇 번 실행해도 같은 결과가 된다.

#### 주의점 (구현 전에 개발가이드 v5.0과 실제 호출로 확인할 것)

- `boxoffice`의 기간 지정 방법(`stdate`·`eddate`로 임의 기간을 지정할 수 있는지, 개발가이드에서 "필수"로 된 `date`의 처리)과 과거 기간을 조회할 수 있는지.
- `boxoffice`가 한 번에 돌려주는 행 수(몇 위까지 돌려주는지). 숨긴 공연을 빼고 10건을 채우려면 10건보다 많이 와야 한다.
- `boxStatsCate`를 지역(서울)으로 거를 수 있는지. **거를 수 없으면 전국 비율이 되므로** 사람에게 확인한다.
- `prfawad`·`prfstsPrfBy`의 조회 조건(기간 상한, 지역, 페이지)과 `prfdtcnt`가 기간 안의 횟수인지 누계인지.
- 장르 값(공통코드 목록 `kopis_openapi_code_v3.7`은 아직 받지 않음).

#### 미결 (사람에게 확인하고 싶은 것)

- F-32 ② "상연 횟수"가 어느 기간의 횟수인지(개막부터 누계 / 최근 기간 등). 요건에 적혀 있지 않다.
- F-34가 "서울의" 비율이어야 하는지(`boxStatsCate`로 지역을 거를 수 없는 경우).
- 인기 급상승의 "대상"을 현재 기간 상위 10위로 읽어도 되는지(위 "요건 해석").
- 공연 수집을 "오늘부터 180일 후까지"로 해도 되는지(그보다 뒤에 시작하는 공연은 180일 이내가 되고 나서 표시된다).
- 주간·월간을 "전날까지 7일·30일"(달력 주·월이 아님)로 해도 되는지. F-33 ②의 "전주", "전월"을 "그 앞 7일·30일"로 읽고 있다.

# 0013. 認証はサーバーのセッション（Spring Security）で行う

- 日付: 2026-11-05
- 状態: 採用（2026-11-05、人間が決定）
- 関係する要件: F-12〜F-18, F-24, F-25, F-35, N-05 ②〜⑤（T-04）

## 背景

- メールアドレス・パスワードでログインする（F-13、U-17）。一般ユーザーと管理者の権限を区別する（F-24, F-25）。
- 連続5回の失敗でロックし、成功で回数を初期化する。ロック中は正しいパスワードでもログインできない（F-14）。管理者もロックの対象（F-14 ⑦）。
- ログアウトでき、一定時間操作しないと自動でログアウトする（F-35）。時間の値は工程3で決める（R-26）。
- パスワードはハッシュで保存する（N-05 ②）。通信は HTTPS（N-05 ①）。
- 人間の決定 T-04: 認証方式は architect に任せる（要件と費用を基準に比較して提案する）。
- 画面は Angular、API は Spring Boot。Nginx で同じオリジンにする（0010）。

## 決定

1. **Spring Security を使い、サーバーのセッション（HTTP セッション + Cookie）で認証する。** `spring-boot-starter-security` を追加する。これは新しいライブラリの追加であり、この ADR の採用をもって導入を認める。
2. セッションは**アプリの中（サーブレットコンテナのメモリ）**に持つ。サーバーは1台（0010）なので共有の仕組みはいらない。アプリを再起動するとログインしている人はログアウトされる（N-06 で許容）。
3. **自動ログアウト（F-35 ③）**: セッションのタイムアウトを **30 分**にする（`server.servlet.session.timeout=30m`。Spring Boot の既定値と同じ）。リクエストのたびに残り時間が戻るので、「最後の操作から 30 分」でログアウトされる。**30 分は人間が決定した**（2026-11-05。R-26 で工程3に決めるとされた値）。
4. **ログアウト（F-35 ①）**: サーバーでセッションを無効にし、Cookie を消す。
5. **ログイン試行の制限（F-14）**: 認証の処理の中で、アカウントごとに「連続の失敗回数」と「ロック中かどうか」を DB で管理する。
   - 失敗したら回数を1増やし、5 になったらロックする。成功したら 0 に戻す。
   - ロック中は、パスワードが正しくてもログインを拒否する。
   - 解除は (a) reCAPTCHA の通過（0011）とメールの再認証（0012）の両方、または (b) パスワードの再設定（F-15）。
   - この管理は方式（セッション・トークン）によらずサーバー側で必要。必要なデータ項目は db-designer に渡す。
6. **パスワードの保存（N-05 ②）**: Spring Security の `DelegatingPasswordEncoder`（既定は bcrypt）でハッシュにする。
7. **権限（F-24, F-25）**: 役割を「一般ユーザー」「管理者」の2つにし、管理者の API はサーバーで役割を確かめる。
8. **Cookie と CSRF**:
   - セッションの Cookie は `HttpOnly`・`Secure`・`SameSite=Lax`。
   - CSRF 対策は Spring Security の SPA 向けの設定（`csrf.spa()`。トークンを Cookie `XSRF-TOKEN` で渡し、Angular の HttpClient がヘッダー `X-XSRF-TOKEN` で返す）を使う。
9. **パスワード変更・退会のとき**: 本人のセッションを無効にする（F-16 ②・F-18 ②）。ほかの端末に残っているセッションは、リクエストのたびにアカウントの状態（退会済みなど）を確かめて拒否する。詳しくは 06 で決める。

## 検討した選択肢

| 観点 | **サーバーのセッション** | トークン（JWT を Authorization ヘッダーで送る） |
|---|---|---|
| 自動ログアウト（F-35 ③） | タイムアウトの設定だけで「最後の操作から N 分」になる | トークンの期限は発行時に決まる。「最後の操作から」にするには、短い期限 + 更新トークンの仕組みを自分で作る必要がある |
| ログアウト（F-35 ①②） | セッションを消せば、すぐ使えなくなる | 期限まで有効なので、無効にしたトークンの一覧をサーバーで持つ必要がある（結局サーバーに状態を持つ） |
| ロック（F-14） | DB で管理（どちらも同じ） | DB で管理（どちらも同じ）。発行済みのトークンは期限まで使える |
| 退会・パスワード変更 | セッションを消せる | 発行済みのトークンを止める仕組みが別に必要 |
| 画面の実装（Angular） | Cookie は自動で送られる。CSRF のヘッダーは Angular の標準機能で付く | トークンの保存場所（localStorage は XSS で読まれる）と、ヘッダーを付ける処理を作る |
| ライブラリ | `spring-boot-starter-security` | 上に加えて JWT のライブラリ（`spring-boot-starter-oauth2-resource-server` など） |
| 費用 | 0円（サーバーのメモリだけ） | 0円 |
| 判断 | **採用を提案** | 要件（自動ログアウト・ログアウト）を満たすにはサーバーに状態を持つことになり、利点が少ない |

ほかに、セッションを DB に保存する方式（Spring Session JDBC）も考えた。再起動してもログインが続く利点があるが、ライブラリとテーブルが増える。サーバーが1台で、可用性の目標がない（N-06）ため、今は採らない。

## 結果（良い点・注意点）

### 費用（月0円の範囲か）

| 項目 | 内容 |
|---|---|
| 無料枠・カード | 外部サービスを使わない。費用・カード登録はない |
| 上限・アラートの設定 | 課金がないため不要 |

### 良い点

- 自動ログアウト・ログアウト・退会のときの無効化を、標準の仕組みで満たせる。
- Spring Security の標準の機能（パスワードのハッシュ、CSRF、セッション固定攻撃の対策）を使える。

### 注意点

- アプリの再起動・デプロイで全員がログアウトされる。
- CSRF のトークンはログイン・ログアウトの後に変わる。Angular 側で新しいトークンを受け取る流れを、画面・API の設計（02・03）で確かめる。
- 開発のときは Angular の開発サーバー（4200 番）からアプリ（8080 番）へプロキシで転送し、同じオリジンとして扱う（CORS を開けない）。
- 自動ログアウトされた後の画面の動き（ログイン画面へ移るなど）は 02 で決める。
- 管理者アカウントをサーバーで登録する方法（R-35、F-25 ③）はこの ADR では決めない（工程3の別の設計で決める）。

### 確認した公式ドキュメント（確認日: 2026-11-05）

- Spring Boot のセキュリティ（`spring-boot-starter-security`）: https://docs.spring.io/spring-boot/reference/web/spring-security.html

## 한국어

### 0013. 인증은 서버 세션(Spring Security)으로 한다

- 날짜: 2026-11-05
- 상태: 채택(2026-11-05, 사람이 결정)
- 관련 요건: F-12~F-18, F-24, F-25, F-35, N-05 ②~⑤ (T-04)

### 배경

- 이메일·비밀번호로 로그인한다(F-13, U-17). 일반 사용자와 관리자의 권한을 구분한다(F-24, F-25).
- 연속 5회 실패하면 잠그고, 성공하면 횟수를 초기화한다. 잠긴 동안은 올바른 비밀번호로도 로그인할 수 없다(F-14). 관리자도 잠금 대상(F-14 ⑦).
- 로그아웃할 수 있고, 일정 시간 조작하지 않으면 자동 로그아웃된다(F-35). 시간 값은 공정 3에서 정한다(R-26).
- 비밀번호는 해시로 저장한다(N-05 ②). 통신은 HTTPS(N-05 ①).
- 사람의 결정 T-04: 인증 방식은 architect에게 맡긴다(요건과 비용을 기준으로 비교해 제안).
- 화면은 Angular, API는 Spring Boot. Nginx로 같은 오리진으로 한다(0010).

### 결정

1. **Spring Security를 쓰고 서버 세션(HTTP 세션 + 쿠키)으로 인증한다.** `spring-boot-starter-security`를 추가한다. 새 라이브러리 추가이며, 이 ADR의 채택으로 도입을 허용한다.
2. 세션은 **앱 안(서블릿 컨테이너 메모리)**에 둔다. 서버가 1대(0010)라서 공유 장치는 필요 없다. 앱을 재시작하면 로그인한 사람은 로그아웃된다(N-06에서 허용).
3. **자동 로그아웃(F-35 ③)**: 세션 타임아웃을 **30분**으로 한다(`server.servlet.session.timeout=30m`. Spring Boot 기본값과 같음). 요청할 때마다 남은 시간이 되돌아가므로 "마지막 조작에서 30분" 뒤에 로그아웃된다. **30분은 사람이 결정했다**(2026-11-05. R-26에서 공정 3에 정한다고 한 값).
4. **로그아웃(F-35 ①)**: 서버에서 세션을 무효로 하고 쿠키를 지운다.
5. **로그인 시도 제한(F-14)**: 인증 처리 안에서 계정별 "연속 실패 횟수"와 "잠김 여부"를 DB로 관리한다.
   - 실패하면 횟수를 1 늘리고 5가 되면 잠근다. 성공하면 0으로 되돌린다.
   - 잠긴 동안은 비밀번호가 맞아도 로그인을 거부한다.
   - 해제는 (a) reCAPTCHA 통과(0011)와 메일 재인증(0012) 둘 다, 또는 (b) 비밀번호 재설정(F-15).
   - 이 관리는 방식(세션·토큰)과 관계없이 서버에 필요하다. 필요한 데이터 항목은 db-designer에게 넘긴다.
6. **비밀번호 저장(N-05 ②)**: Spring Security의 `DelegatingPasswordEncoder`(기본은 bcrypt)로 해시한다.
7. **권한(F-24, F-25)**: 역할을 "일반 사용자", "관리자" 2개로 하고, 관리자 API는 서버에서 역할을 확인한다.
8. **쿠키와 CSRF**:
   - 세션 쿠키는 `HttpOnly`·`Secure`·`SameSite=Lax`.
   - CSRF 대책은 Spring Security의 SPA용 설정(`csrf.spa()`. 토큰을 쿠키 `XSRF-TOKEN`으로 넘기고 Angular HttpClient가 헤더 `X-XSRF-TOKEN`으로 돌려준다)을 쓴다.
9. **비밀번호 변경·탈퇴 때**: 본인 세션을 무효로 한다(F-16 ②·F-18 ②). 다른 기기에 남은 세션은 요청할 때마다 계정 상태(탈퇴 등)를 확인해 거부한다. 자세한 것은 06에서 정한다.

### 검토한 선택지

| 관점 | **서버 세션** | 토큰(JWT를 Authorization 헤더로 보냄) |
|---|---|---|
| 자동 로그아웃(F-35 ③) | 타임아웃 설정만으로 "마지막 조작에서 N분"이 된다 | 토큰 기한은 발급 때 정해진다. "마지막 조작에서"로 하려면 짧은 기한 + 갱신 토큰 장치를 직접 만들어야 한다 |
| 로그아웃(F-35 ①②) | 세션을 지우면 바로 못 쓰게 된다 | 기한까지 유효하므로 무효로 한 토큰 목록을 서버에 가져야 한다(결국 서버에 상태를 둔다) |
| 잠금(F-14) | DB로 관리(둘 다 같음) | DB로 관리(둘 다 같음). 발급된 토큰은 기한까지 쓸 수 있다 |
| 탈퇴·비밀번호 변경 | 세션을 지울 수 있다 | 발급된 토큰을 멈추는 장치가 따로 필요하다 |
| 화면 구현(Angular) | 쿠키는 자동으로 보내진다. CSRF 헤더는 Angular 표준 기능으로 붙는다 | 토큰 저장 위치(localStorage는 XSS로 읽힌다)와 헤더를 붙이는 처리를 만든다 |
| 라이브러리 | `spring-boot-starter-security` | 위에 더해 JWT 라이브러리(`spring-boot-starter-oauth2-resource-server` 등) |
| 비용 | 0원(서버 메모리만) | 0원 |
| 판단 | **채택 제안** | 요건(자동 로그아웃·로그아웃)을 충족하려면 서버에 상태를 두게 되어 이점이 적다 |

그 밖에 세션을 DB에 저장하는 방식(Spring Session JDBC)도 생각했다. 재시작해도 로그인이 이어지는 이점이 있지만 라이브러리와 테이블이 늘어난다. 서버가 1대이고 가용성 목표가 없으므로(N-06) 지금은 쓰지 않는다.

### 결과 (좋은 점·주의점)

#### 비용 (월 0원 범위인가)

| 항목 | 내용 |
|---|---|
| 무료 한도·카드 | 외부 서비스를 쓰지 않는다. 비용·카드 등록이 없다 |
| 상한·알림 설정 | 과금이 없으므로 불필요 |

#### 좋은 점

- 자동 로그아웃·로그아웃·탈퇴 때의 무효화를 표준 장치로 충족할 수 있다.
- Spring Security 표준 기능(비밀번호 해시, CSRF, 세션 고정 공격 대책)을 쓸 수 있다.

#### 주의점

- 앱 재시작·배포 때 모두 로그아웃된다.
- CSRF 토큰은 로그인·로그아웃 뒤에 바뀐다. Angular에서 새 토큰을 받는 흐름을 화면·API 설계(02·03)에서 확인한다.
- 개발 때는 Angular 개발 서버(4200번)에서 앱(8080번)으로 프록시로 넘겨 같은 오리진으로 다룬다(CORS를 열지 않는다).
- 자동 로그아웃된 뒤의 화면 동작(로그인 화면으로 이동 등)은 02에서 정한다.
- 관리자 계정을 서버에서 등록하는 방법(R-35, F-25 ③)은 이 ADR에서 정하지 않는다(공정 3의 다른 설계에서 정한다).

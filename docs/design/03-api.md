## 1. 共通の決まり

### 1.1 形式

- REST。ベースのパスは `/api`。JSON（UTF-8）。画面（Angular）と同じオリジンで提供する（Nginx が `/api` をアプリへ転送する。ADR 0010）。
- 日付は `YYYY-MM-DD`、日時は ISO 8601（オフセット付き）。日付の判定（「今日」）はすべて **Asia/Seoul** で行う。

### 1.2 表示言語

- 外部データを返す GET の API は、クエリ `lang`（`ko` または `ja`。既定は `ko`）を受け取る（F-10, F-11）。
- `lang=ja` のときは、翻訳した値と原文の両方を返す。翻訳がない項目は、翻訳がないことが分かる形で返す（画面の表示は 02 の 3.4、P-06）。
- ジャンル・公演の状態・区は、コード（例: ジャンルの KOPIS コード、区の名前の原文）で返し、表示の文言は画面の辞書で訳す（ADR 0007）。

### 1.3 認証・認可（ADR 0013）

- サーバーのセッション（Cookie）で認証する。セッションは最後のリクエストから **30 分**で切れる（R-26、ADR 0013）。
- 状態を変える API（POST・PUT・PATCH・DELETE）は CSRF のトークン（Cookie `XSRF-TOKEN` → ヘッダー `X-XSRF-TOKEN`）が必要。
- 認可の区分（3. の「認可」の列）:

| 区分 | 意味 |
|---|---|
| 全員 | ログイン不要 |
| 全員（内容が変わる） | ログイン不要。ログインしていると返す内容が増える |
| 未ログイン | ログイン不要（ログインしていても使えるが、画面からは使わない） |
| 一般 | 一般ユーザーでログイン。管理者は使えない（403） |
| 管理者 | 管理者でログイン（F-24 ②、F-25） |

- ログインしていないときは 401、権限がないときは 403 を返す（F-24）。

### 1.4 ページング・並び順

- 一覧の API はクエリ `page`（0 から）と `size`（既定 20、最大 100）を受け取り、総件数とページ数を返す。
- 並び順は API ごとに固定する（3. の「並び順」の列）。利用者が並び順を選ぶ機能は置かない（P-15）。

### 1.5 エラー

- エラーの本文は共通の形（エラーコード、メッセージ、入力の誤りのときは項目ごとの内容）にする。詳しい形とコードの一覧は工程4で書く。
- 主なステータス: 400 入力の誤り・業務上の条件に合わない、401 未ログイン・ログインの失敗、403 権限がない・CSRF、404 ない・非表示の公演、409 重複（メールアドレス・ニックネーム・レビュー）、503 外部サービスの上限・停止（メール・reCAPTCHA）。

### 1.6 公開中の公演・表示できる公演

一般ユーザー向けの API は、次の条件で公演を絞る。「今日」は Asia/Seoul。値は管理者の修正を反映した値（F-26）。

| 名前 | 条件 | 使う API | 要件 |
|---|---|---|---|
| 公開中の公演 | 非表示でない、かつ公演終了日 ≥ 今日、かつ公演開始日 ≤ 今日 + 180 日、かつソウルの公演 | API-01, API-02, API-05 | F-01 ①②, F-02 ⑩, F-07 ⑤, F-09 ①, F-27 ② |
| 表示できる公演 | 非表示でない（終わった公演を含む。画面に「終了」と示す） | API-03, API-04, API-10, API-11, API-43, API-44, API-20, API-21 | F-03 ④⑤, F-09 ③④, F-20 ④⑤, F-29 ⑥ |

- 非表示・存在しない公演の詳細は 404（F-03 ⑤）。
- 終わった公演かどうかは、公演終了日と今日で照会のたびに判定する（バッチで状態を書き換えない。ADR 0008 2.）。

## 4. 主な振る舞いの決まり

### 4.1 公演の検索の条件（API-01・API-02。F-02）

| 条件 | クエリ | 複数 | 判定 | 要件 |
|---|---|---|---|---|
| 期間 | `from`, `to` | 1つ | 公演開始日 ≤ `to` かつ 公演終了日 ≥ `from`（1日でも重なる。休演日は見ない） | F-02 ② |
| 区 | `district`（繰り返し） | 複数（OR） | 会場の区が指定した区のどれか（4.2） | F-02 ⑦⑨ |
| 地図の範囲 | `swLat`, `swLng`, `neLat`, `neLng` | 1つ | 会場の座標が範囲の中 | F-02 ⑦ |
| 会場 | `venueId` | 1つ | その会場の公演 | F-02 ⑦ |
| ジャンル | `genre`（繰り返し） | 複数（OR） | 公演のジャンルがどれか | F-02 ④⑨ |
| 公演の状態 | `status`（`ongoing` / `upcoming`。繰り返し） | 複数（OR） | 公演中: 開始日 ≤ 今日 ≤ 終了日。公演予定: 開始日 > 今日 | F-02 ⑤⑨ |
| キーワード | `keyword` | 1つ | 公演名（原文）に含む。`lang=ja` のときは、原文または翻訳した公演名に含む | F-02 ⑥ |

- 種類の違う条件は AND（F-02 ⑧）。区・地図の範囲・会場は同時に指定しない（指定したら 400。P-04）。
- どの条件にも 1.6 の「公開中の公演」の条件が加わる（F-02 ⑩）。
- 会場の座標がない公演は、地図の範囲を指定したときと API-02・API-05 では返さない（P-11）。

### 4.2 公演の区の判定（R-21）

- **確定（設計）**: 会場の区は、KOPIS の施設詳細（`prfplc/{mt10id}`）の住所 `adres` の先頭「서울특별시」に続く「○○구」を取り出し、ソウルの 25 区の一覧と照らして決める。収集（05 の B-01）で会場を保存するときに決めて保存する。
- 理由: 座標から境界の図形で判定する方法は、区の境界のデータ（新しいデータの出どころ）が必要になる。KOPIS の住所は会場ごとにあり、ソウルの公演に限って集めているので、先頭の形がそろう。
- 区を決められない会場（住所がない・形が違う）は区なしとして保存し、件数をバッチの結果に残す（05）。区なしの会場の公演は、区で絞り込んだときだけ結果に出ない（ほかの条件では出る）。

### 4.3 公演詳細の人気順位（O-01。P-02）

- API-03 は、全体とその公演のジャンルの、日次・週次・月次の人気順位（API-20 と同じ期間（4.9）・同じ、非表示を除いて振り直した順位）のうち、その公演が 10 位以内に入っているものを、期間・ジャンル・順位・集計期間（初日・末日）の組で返す（最大 6 組。画面は集計期間と一緒に表示する。02 の SC-02）。

### 4.4 評価（F-30。O-04 はP-03）

- 評価は、表示できる公演のレビュー（退会・削除されたものは残らない）の星の平均とレビュー数。照会のたびに計算する（投稿・編集・削除がすぐ反映される。F-30 ③）。
- 平均は小数第2位を四捨五入して小数第1位にする（P-03）。レビュー数が 0 のときは平均を返さない（画面は「まだレビューがありません」）。

### 4.5 周辺（500m。F-05〜F-07）

- 距離は、会場（または現在地）の座標と駅の座標から、サーバーで球面上の距離（ハバーサインの式）で計算する。Google の API は使わない（ADR 0006）。**500m 以下**を「500m 以内」とする。
- 駅は、ソウル交通公社 1〜8号線のソウルにある駅だけ（取り込みで絞る。05 の B-02）。乗り換え駅は路線ごとに1行。出口番号は返さない（F-05 ④）。
- コインロッカーは駅の座標で距離を判定し、位置の文章（例: 1번 출입구 주변）を返す（F-06 ②③）。
- API-05 の公演は公開中の公演だけ（F-07 ⑤）。現在地の座標はソウルの範囲外でもエラーにしない（結果が0件になる）。

| メールアドレス | 必須、メールアドレスの形、254 文字以内 | F-12 |
| パスワード（新しく設定するもの: API-33・36・41 の新しいパスワード、B-03 の初期パスワード） | 必須。**英字・数字・記号（ASCII の文字）だけで 8〜64 文字、英字と数字を両方含む**（01 の「パスワードのルール」。R-64）。英字は `A`〜`Z`・`a`〜`z`、数字は `0`〜`9`、記号は下の「記号の範囲」。それ以外の文字（ハングル・ひらがな・全角の文字・制御文字など）を1つでも含むと 400。前後の空白を取り除かない（入力のまま判定する） | F-12 ④, F-15 ③, F-16 ③, N-05 ④ |
| ニックネーム | 必須、1〜20 文字（P-05）、前後の空白は除く、ほかのユーザー（**登録が完了したアカウント**。認証前の申込は含まない。4.7）と重複しない | F-12 ②③, F-17 ③ |
| 評価 | 必須、1〜5 の整数 | F-21 ③, F-22 ② |
| レビュー本文 | 任意、1,000 文字以内（P-05） | F-21 ②④, F-22 ② |
| レビューの投稿 | 表示できる公演であること、今日 ≥ 公演開始日（F-21 ⑥⑦）、同じ人の同じ公演のレビューがないこと（409。F-21 ⑤） | F-21 |

- 文字数は Unicode の文字（コードポイント）で数える（すべての項目で同じ）。パスワードは ASCII の文字だけなので、1 文字は UTF-8 で 1 バイトになり、64 文字でも **最大 64 バイト**である。ハッシュ（bcrypt。ADR 0013）が扱える **72 バイトを超えない**（R-64 の理由）。
- **記号の範囲（決定。2026-11-06 人間の決定、Issue #15 コメント 6678921752）**: 印字できる ASCII の文字（0x21〜0x7E）のうち、英字・数字でない 32 文字（`` !"#$%&'()*+,-./:;<=>?@[\]^_`{|}~ ``）。**空白（0x20）は使えない**（01 の R-64 の「記号」に空白を含めない）。空白を1つでも含むと入力の誤り（400）とする。理由: 前後の空白はコピーのときなどに入りやすく、入っていても画面で気づきにくい（ログインできない原因になる）。採らなかった案: 空白も記号に含める（0x20〜0x7E。単語を空白でつなぐパスワードを使える）。
- このルールは**新しく設定するパスワード**にだけ使う。ログイン（API-31）のパスワードと、API-41・42 の現在のパスワードは、必須だけを確かめ、ルールに合わなくても 400 にしない（保存したハッシュと合わないので、パスワードの誤りとして扱う。4.7）。

### 4.7 アカウントの流れ（F-12〜F-15）

- **会員登録の申込（API-33。P-10）**: メールの上限（4.8）を確かめ、上限なら何も保存せず 503。メールアドレスが登録済み（認証を完了したアカウントがある）なら 409。ニックネームが**登録を完了したアカウント**（有効なアカウント。管理者を含む）で使われていれば 409。**認証前の申込はニックネームを押さえない**: 同じニックネームの認証前の申込がほかにあっても受け付ける（人間の決定。Issue #15 コメント 6677710885 の Q-01 の B）。認証前の同じメールアドレスの申込があれば置き換える（前のトークンは無効になる）。認証のメールのリンクは 24 時間有効。
- **メール認証の完了（API-34）**: 1つのトランザクションで、次の順に判定する。
  1. トークンが無効（存在しない・期限切れ・使用済み）なら 400（エラーの種類: トークンが無効）。何も変えない。
  2. 申込のニックネームが、その時点で**登録を完了したアカウント**で使われていれば、**登録は失敗**し 409（エラーの種類: 認証の時点でニックネームが使われている。API-33 の 409 の種類（メールアドレス・ニックネーム）とはエラーコードで見分ける。コードの名前・本文の形は工程4）。このとき、その**認証前の行を削除**する（トークンも一緒に消え、同じリンクはそれ以降 1. の「無効」になる）。行が残らないので、利用者は同じメールアドレスで、別のニックネームですぐ申し込み直せる（02 の SC-06）。
  3. 1・2 に当たらなければ、アカウントを有効にし、トークンを使用済みにする（F-12 ⑦）。
  - 2 の判定から有効にするまでの間に、同じニックネームの別の申込が先に有効になることがある。これを防ぐため、**有効なアカウントの間のニックネームの重複は DB の一意制約でも防ぐ**（認証前の行には効かせない。04 の DB-06 を db-designer が直す）。制約の違反は 2 と同じ扱い（行の削除と 409）にする。
- **F-12 ③ との関係**: F-12 ③「他のユーザーが使っているニックネームでは登録できない」の「登録」は、⑦ のとおりメールの認証の完了で成立する。そのため、申込（API-33）と認証の完了（API-34）の両方で、その時点の登録を完了したアカウントと比べれば ③ を満たす（認証の完了のときに使われていれば、③ により登録できない）。認証前の申込は、⑧ のとおりログインできない状態で、「他のユーザー」に含めない。ニックネームの変更（API-40。F-17 ③）も同じく、登録を完了したアカウントとだけ比べる（認証前の申込と同じニックネームに変えられる。その申込は認証の完了のときに 2. で失敗する）。
- **期限の切れた認証前の行**: B-04（05 の 6.）が毎日 04:00 に削除する。認証前の行はニックネームを押さえないので、残っていても他人の登録を妨げない。削除するのは、使われないメールアドレス・パスワードのハッシュを持ち続けないため（記録の整理）。
  - 削除の前: 同じメールアドレスの申込し直しは置き換えで受け付ける（P-10）。そのメールアドレスでのログインは「認証が済んでいない」を返す（02 の SC-04 の案内のとおり、もう一度会員登録できる）。
  - 削除の後: 同じメールアドレスの申込し直しは、新しい申込として受け付ける。ログインは、存在しないメールアドレスと同じ応答になる。
  - API-33・API-34 は、期限の切れた**ほかの**行の削除を行わない（削除は B-04 だけにまとめる。API-33 の置き換えと API-34 の 2. の削除は、その申込の行だけを対象にする）。
- **ログイン（ADR 0013 5.）**: 認証を完了していないアカウントは、パスワードが正しくてもログインできず「認証が済んでいない」を返す（失敗の回数に数えない。F-12 ⑧）。ロック中は、パスワードが正しくても「ロック中」を返す（F-14 ③）。パスワードの誤りは連続の失敗回数を1増やし、5回でロックする。成功で 0 に戻す（F-14 ①②）。存在しないメールアドレスは、パスワードの誤りと同じ応答にする。
- **パスワード再設定**: API-35 はアカウントの有無にかかわらず同じ応答（上限のときだけ 503）。リンクは 1 時間有効（P-10）。API-36 で新しいパスワードを設定し、ロック中なら解除し、失敗の回数を 0 にする（F-15 ④）。管理者も使える（F-15 ⑤）。
- **ロック解除（F-14 ④(a)⑤）**: API-37 は reCAPTCHA のトークンを `CreateAssessment` で検証し（ADR 0011）、通過したときだけ、ロック中のアカウントに再認証のメールを送る（アカウントの有無・ロックの有無にかかわらず同じ応答）。検証の失敗は 400、reCAPTCHA の上限・停止は 503。リンクは 1 時間有効（P-10）。API-38 でトークンが有効ならロックを解除し、失敗の回数を 0 にする。
- トークンはランダムな値を使い、保存するときはハッシュにする。1回使ったトークンは無効にする。

### 4.8 メールの1日の上限（N-06 ②。P-08）

- メールを送る前に、**直近 24 時間**に送った数を数え、400 通に達していれば送らず、API は 503（エラーコードでメールの上限と分かる形）を返す。上限に達したことをログに残す（ADR 0012）。
- 送信に失敗したとき（Gmail の SMTP のエラー）も 503 を返し、会員登録の申込は保存しない。

### 4.9 人気順位の表示の期間（P-12。01 F-29 ④・F-33 ②、R-62）

- **表示する期間**: API-20・API-21・API-03 は、期間の種類（日・週・月）とジャンル（全体を含む）の組ごとに、すでに終わった期間のうち**順位の収集が終わっている直近の期間**を使い、その集計期間（初日・末日）を返す。
  - 「収集が終わっている」は、B-01 の S2 がその組・その期間の照会と保存を最後まで終えたことで判断する（05 の 3.4。提供元の結果が 0 件でも「終わっている」）。行が保存されているかどうかでは判断しない（0 件の期間と未収集の期間を見分けるため）。
  - 直近の終わった期間（日次は前日、週次は先週（月〜日）、月次は先月。Asia/Seoul）の収集が終わっていれば、その期間になる。終わっていなければ1つ前の期間になる。日付が変わってから B-01（06:00 起動）の S2 が終わるまでがこの場合に当たる。収集の失敗が続いたときは、さらに前の期間になることがある（それでも「収集が終わっている直近の期間」であり、集計期間を一緒に返すので F-29 ④ を満たす）。
  - 組ごとに決めるので、S2 の途中（一部のジャンルだけ保存が済んだとき）に照会すると、ジャンルによって集計期間が違うことがある。画面は返された集計期間をそのまま表示する。
- **人気急上昇（API-21）**: 上の期間を現在の期間とし、その1つ前の期間（暦の上で1つ前。F-33 ②）と比べる。1つ前の期間の収集が終わっていないときは、比べず、現在の期間の集計期間・直前の期間の集計期間と「直前の期間の順位がない」ことを返す（画面はこれで「比べる期間（{直前の期間の集計期間}）の順位データがないため、人気急上昇を表示できません」を表示する。02 の決定 P-17）。
- 表示できる期間がまったくない（サービスの開始前など）ときは、0 件と「期間がない」ことを返す（画面は「この期間の順位データがありません」）。
- レスポンスの項目の詳細（集計期間の項目名、直前の期間がないときの形）は工程4で書く。
- **公演（performance）に結びつかない順位の行**の扱いは工程4で決める。画面に見える振る舞いが変わる場合は、工程4で人間に確認する（ゲート3 の軽微6。人間の決定: Issue #15 コメント 6678516145）。

### 4.10 管理者の修正（F-26。P-13）

- 修正は項目ごとに保存し、自動収集の値とは別に持つ。表示には「修正した値があればそれ、なければ自動収集の値」を使う。
- 自動収集（B-01）は自動収集の値だけを更新し、修正した値は変えない（F-26 ③④）。取り消すと修正した値を消す（F-26 ⑤）。
- 修正した公演名などの日本語の翻訳は、次の B-01 の翻訳（S7）で作る。

### 1. 공통 규칙

#### 1.1 형식

- REST. 기본 경로는 `/api`. JSON(UTF-8). 화면(Angular)과 같은 오리진으로 제공한다(Nginx가 `/api`를 앱으로 넘긴다. ADR 0010).
- 날짜는 `YYYY-MM-DD`, 일시는 ISO 8601(오프셋 포함). 날짜 판정("오늘")은 모두 **Asia/Seoul**로 한다.

#### 1.2 표시 언어

- 외부 데이터를 돌려주는 GET API는 쿼리 `lang`(`ko` 또는 `ja`. 기본 `ko`)을 받는다(F-10, F-11).
- `lang=ja`일 때는 번역한 값과 원문을 둘 다 돌려준다. 번역이 없는 항목은 번역이 없다는 것을 알 수 있는 형태로 돌려준다(화면 표시는 02의 3.4, P-06).
- 장르·공연 상태·구는 코드(예: 장르의 KOPIS 코드, 구 이름 원문)로 돌려주고, 표시 문구는 화면 사전으로 옮긴다(ADR 0007).

#### 1.3 인증·인가 (ADR 0013)

- 서버 세션(쿠키)으로 인증한다. 세션은 마지막 요청에서 **30분** 뒤 끊긴다(R-26, ADR 0013).
- 상태를 바꾸는 API(POST·PUT·PATCH·DELETE)는 CSRF 토큰(쿠키 `XSRF-TOKEN` → 헤더 `X-XSRF-TOKEN`)이 필요하다.
- 인가 구분(3.의 "인가" 열):

| 구분 | 의미 |
|---|---|
| 모두 | 로그인 불필요 |
| 모두(내용이 바뀜) | 로그인 불필요. 로그인하면 돌려주는 내용이 늘어난다 |
| 비로그인 | 로그인 불필요(로그인해도 쓸 수 있지만 화면에서는 쓰지 않음) |
| 일반 | 일반 사용자로 로그인. 관리자는 쓸 수 없다(403) |
| 관리자 | 관리자로 로그인(F-24 ②, F-25) |

- 로그인하지 않았으면 401, 권한이 없으면 403을 돌려준다(F-24).

#### 1.4 페이지네이션·정렬

- 목록 API는 쿼리 `page`(0부터)와 `size`(기본 20, 최대 100)를 받고, 전체 건수와 페이지 수를 돌려준다.
- 정렬은 API마다 고정한다(3.의 "정렬" 열). 이용자가 정렬을 고르는 기능은 두지 않는다(P-15).

#### 1.5 오류

- 오류 본문은 공통 형태(오류 코드, 메시지, 입력 오류일 때는 항목별 내용)로 한다. 자세한 형태와 코드 목록은 공정 4에서 쓴다.
- 주요 상태 코드: 400 입력 오류·업무 조건에 맞지 않음, 401 비로그인·로그인 실패, 403 권한 없음·CSRF, 404 없음·숨긴 공연, 409 중복(이메일 주소·닉네임·리뷰), 503 외부 서비스 상한·정지(메일·reCAPTCHA).

#### 1.6 공개 중인 공연·표시할 수 있는 공연

일반 사용자용 API는 다음 조건으로 공연을 거른다. "오늘"은 Asia/Seoul. 값은 관리자 수정을 반영한 값(F-26).

| 이름 | 조건 | 쓰는 API | 요건 |
|---|---|---|---|
| 공개 중인 공연 | 숨기지 않았고, 공연 종료일 ≥ 오늘이고, 공연 시작일 ≤ 오늘 + 180일이고, 서울 공연 | API-01, API-02, API-05 | F-01 ①②, F-02 ⑩, F-07 ⑤, F-09 ①, F-27 ② |
| 표시할 수 있는 공연 | 숨기지 않음(끝난 공연 포함. 화면에 "종료"로 표시) | API-03, API-04, API-10, API-11, API-43, API-44, API-20, API-21 | F-03 ④⑤, F-09 ③④, F-20 ④⑤, F-29 ⑥ |

- 숨긴 공연·없는 공연의 상세는 404(F-03 ⑤).
- 끝난 공연인지는 공연 종료일과 오늘로 조회할 때마다 판정한다(배치로 상태를 고쳐 쓰지 않는다. ADR 0008 2.).

### 4. 주요 동작 규칙

#### 4.1 공연 검색 조건 (API-01·API-02. F-02)

| 조건 | 쿼리 | 여러 개 | 판정 | 요건 |
|---|---|---|---|---|
| 기간 | `from`, `to` | 1개 | 공연 시작일 ≤ `to` 그리고 공연 종료일 ≥ `from`(하루라도 겹침. 휴연일은 보지 않음) | F-02 ② |
| 구 | `district`(반복) | 여러 개(OR) | 공연장의 구가 지정한 구 중 하나(4.2) | F-02 ⑦⑨ |
| 지도 범위 | `swLat`, `swLng`, `neLat`, `neLng` | 1개 | 공연장 좌표가 범위 안 | F-02 ⑦ |

| 키워드 | `keyword` | 1개 | 공연명(원문)에 포함. `lang=ja`일 때는 원문 또는 번역한 공연명에 포함 | F-02 ⑥ |

- 종류가 다른 조건은 AND(F-02 ⑧). 구·지도 범위·공연장은 동시에 지정하지 않는다(지정하면 400. P-04).
- 모든 조건에 1.6의 "공개 중인 공연" 조건이 더해진다(F-02 ⑩).
- 공연장 좌표가 없는 공연은 지도 범위를 지정했을 때와 API-02·API-05에서는 돌려주지 않는다(P-11).

#### 4.2 공연의 구 판정 (R-21)

- **확정(설계)**: 공연장의 구는 KOPIS 시설상세(`prfplc/{mt10id}`) 주소 `adres` 앞의 "서울특별시" 뒤에 오는 "○○구"를 꺼내, 서울 25개 구 목록과 대조해 정한다. 수집(05의 B-01)에서 공연장을 저장할 때 정해 저장한다.
- 이유: 좌표로 경계 도형에서 판정하는 방법은 구 경계 데이터(새 데이터 출처)가 필요하다. KOPIS 주소는 공연장마다 있고, 서울 공연만 모으므로 앞부분 형태가 같다.
- 구를 정할 수 없는 공연장(주소 없음·형태가 다름)은 구 없음으로 저장하고, 건수를 배치 결과에 남긴다(05). 구 없는 공연장의 공연은 구로 거를 때만 결과에 나오지 않는다(다른 조건에서는 나온다).

#### 4.3 공연 상세의 인기 순위 (O-01. P-02)

- API-03은 전체와 그 공연 장르의 일간·주간·월간 인기 순위(API-20과 같은 기간(4.9)·같은, 숨긴 공연을 빼고 다시 매긴 순위) 중 그 공연이 10위 안에 든 것을 기간·장르·순위·집계 기간(첫날·마지막 날)의 묶음으로 돌려준다(최대 6묶음. 화면은 집계 기간과 함께 보여준다. 02의 SC-02).

#### 4.4 평점 (F-30. O-04는 P-03)

- 평점은 표시할 수 있는 공연의 리뷰(탈퇴·삭제된 것은 남지 않음)의 별 평균과 리뷰 수. 조회할 때마다 계산한다(작성·수정·삭제가 바로 반영된다. F-30 ③).
- 평균은 소수 둘째 자리에서 반올림해 소수 첫째 자리로 한다(P-03). 리뷰 수가 0이면 평균을 돌려주지 않는다(화면은 "아직 리뷰가 없습니다").

#### 4.5 주변 (500m. F-05~F-07)

- 거리는 공연장(또는 현재 위치) 좌표와 역 좌표로 서버에서 구면 거리(하버사인 공식)로 계산한다. Google API는 쓰지 않는다(ADR 0006). **500m 이하**를 "500m 이내"로 한다.
- 역은 서울교통공사 1~8호선 중 서울에 있는 역만(수집에서 거른다. 05의 B-02). 환승역은 노선마다 1행. 출구 번호는 돌려주지 않는다(F-05 ④).
- 물품보관함은 역 좌표로 거리를 판정하고 위치 설명(예: 1번 출입구 주변)을 돌려준다(F-06 ②③).
- API-05의 공연은 공개 중인 공연만(F-07 ⑤). 현재 위치 좌표가 서울 밖이어도 오류로 하지 않는다(결과가 0건이 된다).

#### 4.6 입력 규칙

| 항목 | 규칙 | 요건 |
|---|---|---|
| 이메일 주소 | 필수, 이메일 형식, 254자 이내 | F-12 |
| 비밀번호(새로 설정하는 것: API-33·36·41의 새 비밀번호, B-03의 초기 비밀번호) | 필수. **영문·숫자·기호(ASCII 문자)만으로 8~64자, 영문과 숫자를 모두 포함**(01의 "비밀번호 규칙". R-64). 영문은 `A`~`Z`·`a`~`z`, 숫자는 `0`~`9`, 기호는 아래 "기호의 범위". 그 밖의 문자(한글·히라가나·전각 문자·제어 문자 등)를 하나라도 포함하면 400. 앞뒤 공백을 제거하지 않는다(입력 그대로 판정한다) | F-12 ④, F-15 ③, F-16 ③, N-05 ④ |
| 닉네임 | 필수, 1~20자(P-05), 앞뒤 공백 제거, 다른 사용자(**가입을 완료한 계정**. 인증 전 신청은 포함하지 않음. 4.7)와 중복 불가 | F-12 ②③, F-17 ③ |
| 평점 | 필수, 1~5 정수 | F-21 ③, F-22 ② |
| 리뷰 본문 | 선택, 1,000자 이내(P-05) | F-21 ②④, F-22 ② |
| 리뷰 작성 | 표시할 수 있는 공연일 것, 오늘 ≥ 공연 시작일(F-21 ⑥⑦), 같은 사람의 같은 공연 리뷰가 없을 것(409. F-21 ⑤) | F-21 |

- 글자 수는 Unicode 문자(코드 포인트)로 센다(모든 항목에서 같음). 비밀번호는 ASCII 문자만이므로 한 글자는 UTF-8로 1바이트가 되고, 64자여도 **최대 64바이트**다. 해시(bcrypt. ADR 0013)가 다룰 수 있는 **72바이트를 넘지 않는다**(R-64의 이유).
- **기호의 범위(결정. 2026-11-06 사람의 결정, Issue #15 코멘트 6678921752)**: 인쇄할 수 있는 ASCII 문자(0x21~0x7E) 중 영문·숫자가 아닌 32자(`` !"#$%&'()*+,-./:;<=>?@[\]^_`{|}~ ``). **공백(0x20)은 쓸 수 없다**(01의 R-64의 "기호"에 공백을 포함하지 않는다). 공백을 하나라도 포함하면 입력 오류(400)로 한다. 이유: 앞뒤 공백은 복사할 때 등에 들어가기 쉽고, 들어가 있어도 화면에서 알아차리기 어렵다(로그인할 수 없는 원인이 된다). 채택하지 않은 안: 공백도 기호에 포함한다(0x20~0x7E. 단어를 공백으로 잇는 비밀번호를 쓸 수 있다).
- 이 규칙은 **새로 설정하는 비밀번호**에만 쓴다. 로그인(API-31)의 비밀번호와 API-41·42의 현재 비밀번호는 필수만 확인하고, 규칙에 맞지 않아도 400으로 하지 않는다(저장한 해시와 맞지 않으므로 비밀번호 오류로 다룬다. 4.7).

#### 4.7 계정 흐름 (F-12~F-15)

- **회원가입 신청(API-33. P-10)**: 메일 상한(4.8)을 확인하고, 상한이면 아무것도 저장하지 않고 503. 이메일 주소가 가입됨(인증을 마친 계정이 있음)이면 409. 닉네임이 **가입을 완료한 계정**(유효한 계정. 관리자 포함)에서 쓰이고 있으면 409. **인증 전 신청은 닉네임을 차지하지 않는다**: 같은 닉네임의 인증 전 신청이 따로 있어도 받는다(사람의 결정. Issue #15 코멘트 6677710885의 Q-01의 B). 인증 전의 같은 이메일 주소 신청이 있으면 대체한다(이전 토큰은 무효가 된다). 인증 메일 링크는 24시간 유효.
- **메일 인증 완료(API-34)**: 하나의 트랜잭션으로 다음 순서로 판정한다.
  1. 토큰이 무효(없음·기한 만료·사용됨)이면 400(오류 종류: 토큰이 무효). 아무것도 바꾸지 않는다.
  2. 신청한 닉네임이 그 시점에 **가입을 완료한 계정**에서 쓰이고 있으면 **가입은 실패**하고 409(오류 종류: 인증 시점에 닉네임이 쓰이고 있음. API-33의 409 종류(이메일 주소·닉네임)와는 오류 코드로 구별한다. 코드 이름·본문 형태는 공정 4). 이때 그 **인증 전 행을 삭제**한다(토큰도 함께 지워지고, 같은 링크는 그 뒤로 1.의 "무효"가 된다). 행이 남지 않으므로 이용자는 같은 이메일 주소로, 다른 닉네임으로 바로 다시 신청할 수 있다(02의 SC-06).
  3. 1·2에 해당하지 않으면 계정을 유효로 하고 토큰을 사용됨으로 한다(F-12 ⑦).
  - 2의 판정부터 유효로 할 때까지 사이에 같은 닉네임의 다른 신청이 먼저 유효가 될 수 있다. 이를 막기 위해 **유효한 계정 사이의 닉네임 중복은 DB 유일 제약으로도 막는다**(인증 전 행에는 적용하지 않는다. 04의 DB-06을 db-designer가 고친다). 제약 위반은 2와 같은 처리(행 삭제와 409)로 한다.
- **F-12 ③과의 관계**: F-12 ③ "다른 사용자가 쓰고 있는 닉네임으로는 가입할 수 없다"의 "가입"은 ⑦대로 메일 인증 완료로 성립한다. 따라서 신청(API-33)과 인증 완료(API-34) 양쪽에서 그 시점의 가입을 완료한 계정과 비교하면 ③을 충족한다(인증 완료 때 쓰이고 있으면 ③에 따라 가입할 수 없다). 인증 전 신청은 ⑧대로 로그인할 수 없는 상태이며 "다른 사용자"에 포함하지 않는다. 닉네임 변경(API-40. F-17 ③)도 마찬가지로 가입을 완료한 계정과만 비교한다(인증 전 신청과 같은 닉네임으로 바꿀 수 있다. 그 신청은 인증 완료 때 2.에서 실패한다).
- **기한이 지난 인증 전 행**: B-04(05의 6.)가 매일 04:00에 삭제한다. 인증 전 행은 닉네임을 차지하지 않으므로 남아 있어도 다른 사람의 가입을 막지 않는다. 삭제하는 것은 쓰이지 않는 이메일 주소·비밀번호 해시를 계속 갖고 있지 않기 위해서다(기록 정리).
  - 삭제 전: 같은 이메일 주소의 재신청은 교체로 받는다(P-10). 그 이메일 주소로 로그인하면 "인증이 끝나지 않음"을 돌려준다(02의 SC-04 안내대로 다시 회원가입할 수 있다).
  - 삭제 후: 같은 이메일 주소의 재신청은 새 신청으로 받는다. 로그인은 없는 이메일 주소와 같은 응답이 된다.
  - API-33·API-34는 기한이 지난 **다른** 행의 삭제를 하지 않는다(삭제는 B-04에만 모은다. API-33의 교체와 API-34의 2.의 삭제는 그 신청의 행만 대상으로 한다).
- **로그인(ADR 0013 5.)**: 인증을 마치지 않은 계정은 비밀번호가 맞아도 로그인할 수 없고 "인증 안 됨"을 돌려준다(실패 횟수에 세지 않음. F-12 ⑧). 잠긴 동안은 비밀번호가 맞아도 "잠김"을 돌려준다(F-14 ③). 비밀번호가 틀리면 연속 실패 횟수를 1 늘리고 5회에서 잠근다. 성공하면 0으로 되돌린다(F-14 ①②). 없는 이메일 주소는 비밀번호가 틀렸을 때와 같은 응답으로 한다.
- **비밀번호 재설정**: API-35는 계정 유무와 관계없이 같은 응답(상한일 때만 503). 링크는 1시간 유효(P-10). API-36에서 새 비밀번호를 설정하고, 잠겨 있으면 풀고 실패 횟수를 0으로 한다(F-15 ④). 관리자도 쓸 수 있다(F-15 ⑤).
- **잠금 해제(F-14 ④(a)⑤)**: API-37은 reCAPTCHA 토큰을 `CreateAssessment`로 검증하고(ADR 0011), 통과했을 때만 잠긴 계정에 재인증 메일을 보낸다(계정 유무·잠김 여부와 관계없이 같은 응답). 검증 실패는 400, reCAPTCHA 상한·정지는 503. 링크는 1시간 유효(P-10). API-38에서 토큰이 유효하면 잠금을 풀고 실패 횟수를 0으로 한다.
- 토큰은 무작위 값을 쓰고, 저장할 때는 해시로 한다. 한 번 쓴 토큰은 무효로 한다.

#### 4.8 메일 하루 상한 (N-06 ②. P-08)

- 메일을 보내기 전에 **최근 24시간**에 보낸 수를 세어, 400통에 도달했으면 보내지 않고 API는 503(오류 코드로 메일 상한임을 알 수 있는 형태)을 돌려준다. 상한 도달을 로그에 남긴다(ADR 0012).
- 발송에 실패했을 때(Gmail SMTP 오류)도 503을 돌려주고, 회원가입 신청은 저장하지 않는다.

#### 4.9 인기 순위의 표시 기간 (P-12. 01 F-29 ④·F-33 ②, R-62)

- **보여주는 기간**: API-20·API-21·API-03은 기간 종류(일·주·월)와 장르(전체 포함)의 조합마다, 이미 끝난 기간 중 **순위 수집이 끝난 가장 최근 기간**을 쓰고, 그 집계 기간(첫날·마지막 날)을 돌려준다.
  - "수집이 끝났다"는 B-01의 S2가 그 조합·그 기간의 조회와 저장을 끝까지 마친 것으로 판단한다(05의 3.4. 제공처 결과가 0건이어도 "끝났다"). 행이 저장되어 있는지로는 판단하지 않는다(0건인 기간과 수집하지 않은 기간을 구별하기 위해).
  - 가장 최근에 끝난 기간(일간은 전날, 주간은 지난주(월~일), 월간은 지난달. Asia/Seoul)의 수집이 끝났으면 그 기간이 된다. 끝나지 않았으면 하나 앞 기간이 된다. 날짜가 바뀐 뒤 B-01(06:00 기동)의 S2가 끝날 때까지가 이 경우다. 수집 실패가 이어지면 더 앞 기간이 될 수 있다(그래도 "수집이 끝난 가장 최근 기간"이고 집계 기간을 함께 돌려주므로 F-29 ④를 충족한다).
  - 조합마다 정하므로, S2 도중(일부 장르만 저장이 끝났을 때)에 조회하면 장르에 따라 집계 기간이 다를 수 있다. 화면은 돌려받은 집계 기간을 그대로 보여준다.
- **인기 급상승(API-21)**: 위 기간을 현재 기간으로 하고, 그 하나 앞 기간(달력상 하나 앞. F-33 ②)과 비교한다. 하나 앞 기간의 수집이 끝나지 않았으면 비교하지 않고, 현재 기간의 집계 기간·직전 기간의 집계 기간과 "직전 기간의 순위가 없음"을 돌려준다(화면은 이것으로 "비교할 기간({직전 기간의 집계 기간})의 순위 데이터가 없어 인기 급상승을 표시할 수 없습니다"를 보여준다. 02의 결정 P-17).
- 보여줄 수 있는 기간이 전혀 없을 때(서비스 시작 전 등)는 0건과 "기간이 없음"을 돌려준다(화면은 "이 기간의 순위 데이터가 없습니다").
- 응답 항목의 상세(집계 기간의 항목명, 직전 기간이 없을 때의 형태)는 공정 4에서 쓴다.
- **공연(performance)과 연결되지 않는 순위 행**의 처리는 공정 4에서 정한다. 화면에 보이는 동작이 바뀌는 경우에는 공정 4에서 사람에게 확인한다(관문 3의 경미 6. 사람의 결정: Issue #15 코멘트 6678516145).

#### 4.10 관리자 수정 (F-26. P-13)

- 수정은 항목별로 저장하고 자동 수집 값과 따로 둔다. 표시에는 "수정한 값이 있으면 그것, 없으면 자동 수집 값"을 쓴다.
- 자동 수집(B-01)은 자동 수집 값만 갱신하고 수정한 값은 바꾸지 않는다(F-26 ③④). 취소하면 수정한 값을 지운다(F-26 ⑤).
- 수정한 공연명 등의 일본어 번역은 다음 B-01 번역(S7)에서 만든다.

#### 6.1 역방향 확인 (불필요한 것이 없음)

- 모든 화면(02의 2.)에 요건 ID가 있다. SC-99는 F-03 ⑤·F-24 때문.
- 모든 API(3.)에 요건 ID가 있다. API-02(지도 마커)·API-06(공연장 후보)은 F-01·F-02 화면 조작 때문, API-30은 F-13·F-24·F-35의 상태 표시 때문.
- **3.의 "요건 ID" 열과 이 표는 요건과 API의 조합으로 일치시킨다**(관문 3의 경미 1에서 확인했다). 예외는 이 표에서 "1.2의 모든 API" "모든 API의 인가(1.3)"로 묶어 쓴 행(F-10·F-11·F-24·N-01)뿐이다. 3.의 열에는 그 요건의 기준에 API의 동작이 직접 해당하는 것만 쓴다(F-11 ②의 원문을 돌려주는 API-01·03~05, F-24 ①의 API-10, F-24 ③의 API-12·13, 로그인 상태를 돌려주는 API-30).
- 모든 배치(05)에 요건 ID가 있다.
- API 열이 "—"인 기능 요건은 F-36뿐. F-36은 브라우저 안에서만 끝난다(전환한 값을 `localStorage`에 기억한다. 02의 3.8)므로 API를 두지 않는다. 로그인한 이용자의 설정으로 서버에 저장하는 기능은 요건에 없다(F-36 ③은 "브라우저에 기억").
- 요건에 없는 기능(예: 리뷰 "좋아요", 알림, 검색 조건 저장, 메일 재전송 버튼)은 두지 않았다(X-05~X-07 등).
